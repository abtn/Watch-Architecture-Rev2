# RW-5 Shared Contract — Freeze Proposal

**Decision status:** Proposed for Operator review; not yet frozen.
**Document purpose:** settle the shared time, decay, locking, replay, and Task-production contracts before RW-5 implementation and before RW-4 dormant-Thread reactivation.
**Baseline:** `main` at `5aecf096b077ab34bc7c8fb09cb750a59a19c335` (PR #181 merge).
**Scope of this proposal:** documentation and source-backed design only. It does not authorize production code, schema changes, migrations, scheduler deployment, provider calls, persistent-database operations, or RW3.4 acceptance.

## 1. Decision requested

Approve or correct the proposed contracts in §4. The intent is to freeze the shared RW-5/RW-4 concurrency boundary once, then implement one stream at a time:

1. RW-5 shared contract freeze.
2. RW-5 implementation and proof.
3. RW4-1 SignalDisposition persistence.
4. RW4-2 triage Task identity and TaskRuntime boundary.
5. RW4-3 deterministic matching/commit, initially without dormant-Thread reactivation.
6. RW4-4 bounded Context retrieval after its own gates.
7. D6-gated dormant-Thread reactivation and RW4-5 integrated proof.

RW4-1 and RW4-2 are not to run in parallel. Each implementation stream requires its own explicit authorization and reviewed proof subset. RW4-0 remains an umbrella design-closure milestone, not a blanket implementation authorization.

## 4. Proposed RW-5 shared contract

### 4.1 Task production, identity, and authority

**Proposed contract:**

- RW-5 core provides a typed, idempotent application boundary that creates one `apply_decay` Task for one Team, pins the immutable request and TeamPolicy version, and persists the request Event atomically.
- The creator derives Team authority from a trusted host boundary, never from model output or an untrusted worker payload. Production host authentication/composition remains an external integration boundary; this proposal does not invent it.
- A periodic scheduler/host trigger is a separate integration slice, **RW5-P**. It may invoke the typed creator but may not mutate world memory, execute Tasks, or become a second runtime. The existing TaskDispatcher remains `ingest_source`-only.
- RW-5 core acceptance covers deterministic creation/execution from a valid typed invocation. It does not claim autonomous periodic operation. **RW5-P is required before foundation exit/R8 can claim scheduled decay is operational.**

The Task table has no generic idempotency-key column. The proposed database identity is a deterministic UUIDv5 Task primary key from a dedicated, versioned namespace and canonical `(team_id, operation, trusted_schedule_slot)`. The schedule slot is trusted host metadata, not model-selected data. For a manual invocation, use an equivalent caller-generated idempotency token in a distinct, explicitly typed identity form. The captured `as_of` timestamp is deliberately **not** part of the Task identity: it is generated only during creation and must be reused by replay.

The database primary-key constraint arbitrates concurrent creators. A creator that finds the deterministic Task ID validates its immutable request and returns the original Task, original `as_of`, and original policy pin—even if the current TeamPolicy has since advanced. A changed semantic request under the same identity is a conflict. The request Event and Task row are one transaction. Do not take an existing Task row lock after acquiring the Team lock; validate immutable request data without reversing TaskRuntime's Task → Team lock order. Golden vectors, unique-conflict races, and concurrent PostgreSQL tests are required.

The Kernel/application boundary must enforce that only the typed creator can create `apply_decay` Tasks. A convention or worker-side check is insufficient. No generic Task-creation permission is added.

### 4.2 Authoritative time: immutable instant plus serialized history watermark

**Decision proposed:** after acquiring the Team serialization lock and then the clock-health singleton FOR SHARE lock, validate current clock health and obtain one UTC database clock observation with PostgreSQL clock_timestamp(). Derive the Task's immutable `as_of` as `GREATEST(database_clock_timestamp, last_epoch_clock_at)` within the active decay epoch, and persist both the epoch ID and that epoch-scoped `as_of` in the canonical Task request/Event before releasing the lock. The Task fingerprint includes both. Do not use Task.created_at: PostgreSQL now() is transaction-start time and the Task may wait in a queue.

**A wall clock is not an ordering key.** clock_timestamp() can move backwards after a host clock adjustment. Separate elapsed-time measurement from history ordering:

- Add a database-enforced, monotonically increasing per-Team world_memory_revision (or prove an equivalent). Every accepted write that creates or changes a Hypothesis, adds an eligible supporting/challenging EvidenceLink, or writes a ConfidenceChange acquires the Team lock, increments the revision once for that transaction, and persists that revision on affected immutable history records and corresponding Events.
- Task creation captures both as_of and the current Team revision watermark while holding the same Team lock. The watermark defines which committed history existed at the Task's serialized cutoff; as_of is used for elapsed-window arithmetic.
- Persist a per-Team, per-epoch non-decreasing logical clock under the Team lock, computed as `GREATEST(database_clock_timestamp, last_epoch_clock_at)`. The monotonicity invariant is scoped to one decay epoch, not across epochs. Each Task and each relevant history timestamp is paired with its epoch ID; timestamps from different epochs are never compared or used to calculate one another's elapsed windows. The Team's `world_memory_revision` remains globally monotonic across epochs and is the sole cross-epoch history-ordering authority.
- A new epoch is the only permitted rebase boundary. On explicit incident recovery, while holding the Team lock, create a new immutable epoch record and initialize its `last_epoch_clock_at` from the corrected, currently validated database UTC instant. Do not carry the previous epoch's possibly corrupted clock maximum into the new epoch. Preserve the old epoch clock and all old Task/history pins unchanged for audit; reject/defer every old-epoch Task. Create new per-Hypothesis recovery baselines at the new epoch origin. Since epoch IDs differ, the new epoch's lower clock origin does not violate the within-epoch monotonicity invariant or create ambiguous decay windows.
- Forward discontinuity detection must not compare Team inactivity with an arbitrary maximum interval. It requires an independent clock-health authority that compares database wall-clock progression with a monotonic elapsed-time source (or an equivalent managed-database clock-step/offset signal). Let `Δdb` be elapsed database wall time and `Δmono` the independently measured monotonic elapsed time between samples. A forward discontinuity is raised when `Δdb - Δmono` exceeds the explicitly configured `max_forward_clock_step`; a backward discontinuity is raised when `Δmono - Δdb` exceeds the separately and explicitly configured `max_backward_clock_step`; either may also be raised by a provider-reported clock-step/offset breach. Both step thresholds and `max_clock_health_sample_age` must be explicitly configured and justified; none has an implicit default. Ordinary inactivity does not trigger either detector. A smaller backward movement that remains within the configured tolerance does not reverse the epoch clock: `GREATEST(database_clock_timestamp, last_epoch_clock_at)` holds the logical clock steady until database UTC catches up. A threshold breach latches the same fail-closed clock incident and requires the same controlled recovery/new-epoch procedure; do not silently treat a material backward step as healthy merely because the logical clock is clamped.
- Clock health is a durable, versioned database-scoped singleton state (the database clock is shared by all Teams) with a monotonically increasing health generation, current status (`healthy` or incident-latched), source identity, last sample ID, database-clock observation, independent monotonic observation, configuration version, and sample expiry. A healthy sample is usable only while its age, measured exclusively against the same independent monotonic source and never against database wall time, is within `max_clock_health_sample_age`. The health monitor locks only this singleton and never takes a Team lock; Task creation/execution, accepted history writers, epoch transitions, and recovery acquire its shared lock after their Team lock, preserving a one-way lock order. Missing, stale, unavailable, malformed, or source-mismatched health evidence fails closed with stable reason `database_clock_health_unavailable`; an observed/latching breach fails closed with `database_clock_discontinuity`. If the deployment cannot provide this independent signal and freshness guarantee, RW-5 decay remains disabled.
- Task creation, decay execution, every accepted history-writing transaction that advances the epoch clock, and every epoch transition validate clock health inside their database transaction after acquiring the Task (when applicable), Team, and clock-health singleton locks in the canonical order. At the validation point, the participant checks the durable singleton generation/status and validates a fresh independent sample from the configured source. It then retains the singleton FOR SHARE lock through commit. Immediately before commit it rechecks the durable generation/status while still holding that lock; it does not claim to atomically re-query an external clock source at the database commit boundary.
- **Incident linearization is the durable latch commit, not external detection time.** The independent monitor may observe a clock breach before it can acquire the singleton FOR UPDATE lock. That observation is evidence for the monitor to latch; it does not itself mutate the database health generation or retroactively invalidate a participant that already holds FOR SHARE. If a participant acquired FOR SHARE first, it is serialized before the incident: it may commit using the healthy generation it validated, and the monitor can latch the incident only after that participant commits or rolls back. This remains true if the monitor's external observation happened earlier in wall-clock time. If the monitor acquires FOR UPDATE and commits the incident generation first, every later participant sees the latched generation/status and fails closed. The database commit that changes the singleton to incident is the single ordering point; there is no claim that asynchronous detection time is an atomic fence.
- This ordering is an explicit first-release choice. It permits an already-admitted transaction holding the shared health lock to finish before the incident becomes effective in the database. Bound that exposure with a configured maximum participant transaction/lock duration, bounded database waits, and monitoring of delayed incident latching; do not allow unbounded transactions to hold the shared lock. If the deployment requires a breach to invalidate all in-flight transactions from the instant an external detector first observes it, this row-lock protocol is insufficient. Stop and design a stronger source-provided fencing/lease mechanism whose revocation is enforced at the commit boundary; do not describe an asynchronous provider recheck as that guarantee.
- The health monitor takes only the singleton FOR UPDATE lock and never acquires a Team lock. It must publish/commit the new generation/status before reporting the incident as durably latched. A monitor blocked behind a participant must expose the pending-latch condition operationally; it must not bypass the lock or acquire Team to force progress. If the source cannot provide a fresh independent sample at participant validation, or the durable singleton cannot be read/locked transactionally, RW-5 remains disabled.
- A forward or backward breach blocks new participants once its incident generation is durably latched. While latched, typed decay Task creation and decay execution are blocked; already admitted Tasks that have not passed the serialized health check defer without ConfidenceChange, summary Event, successful Outcome, epoch-clock advance, or catch-up. A participant already holding the shared lock is ordered before the latch and may finish as specified above. Do not advance any epoch clock using a suspect database timestamp.
- Every successful Task creation and every accepted history-writing transaction that participates in the RW-5 history contract must, while holding the Team lock followed by the shared clock-health singleton lock and after validating clock health, atomically persist `last_epoch_clock_at = GREATEST(database_clock_timestamp, last_epoch_clock_at)` in the same transaction as its Task/request Event or accepted history writes. A rollback advances neither the logical clock nor the corresponding revision/history. This is required even when the transaction has no elapsed decay window to apply. Task creation also captures the Team revision watermark in that same serialized transaction.
- Recovery is explicit: correct the database clock/source, obtain the configured consecutive healthy samples from the same verified source, and require Operator clearance of the latched incident. Under the Team lock followed by the shared clock-health singleton lock, clearance creates the new epoch, initializes its clock origin from the corrected validated database instant, and writes immutable per-Hypothesis recovery baselines. It discards unprocessed windows spanning the incident instead of applying a potentially spurious irreversible catch-up. Record the incident, threshold/config version, health generation, detection interval, clearance actor/time, old/new epoch IDs, and new baseline references for audit.
- **Policy/algorithm epoch transition ownership is deliberately constrained.** A TeamPolicy publication or decay-algorithm version change may become active for RW-5 only through the trusted Kernel/application boundary that authoritatively publishes that version. That same transaction must acquire the Team serialization lock followed by the shared clock-health singleton lock, validate the current clock-health generation, create exactly one immutable successor decay epoch, capture its Team revision and epoch-origin instant, create the complete immutable baseline set for every Hypothesis whose canonical lifecycle status is `active` at the transition's serialized Team-revision cutoff (excluding `superseded` and `rejected` Hypotheses), and publish/activate the policy or algorithm pin atomically. The epoch record must carry the exact policy and algorithm versions and a unique `(team_id, predecessor_epoch_id, transition_kind, target_version)` identity (or an equally strong database-enforced identity); baselines must be unique per `(epoch_id, hypothesis_id)`. Concurrent publishers serialize on the Team lock; the loser must load and validate the winning epoch and must not create a second baseline set. Task creation takes the same Team lock and reads the active epoch only after any publisher transaction commits, so it either pins the old complete epoch or the new complete epoch, never a partial transition. Algorithm-only changes use this same trusted Kernel transition boundary; RW-5 does not add a parallel policy publisher or infer epochs from configuration at Task execution.
- **Current integration limitation:** the production TeamPolicy publisher/lock-serialization boundary is not proven (`RW-POL-01` remains PARTIAL). Therefore this proposal does not assume that the required transition owner currently exists. Until that boundary is separately implemented/reviewed and can atomically perform the transition above, TeamPolicy or algorithm-version changes that would require a new epoch are unsupported for RW-5: do not activate the changed version for decay, do not synthesize baselines from the Task creator, and keep decay disabled/deferred for the affected Team. Initial RW-5 activation and clock-incident recovery must use the same atomic epoch/baseline invariants under explicit Operator authorization. This is an implementation prerequisite and proof obligation, not authorization to modify the production publisher.
- Team revision, not timestamp sorting or UUID ordering, is the primary order for accepted history. A stable record ID may break ties for EvidenceLink records when no domain ordering exists; it must not determine confidence-transition order.
- ConfidenceChange rows for one Hypothesis may share a Team revision when one accepted transaction performs multiple actual transitions (for example, bounded catch-up across several elapsed windows). Each such row must carry a positive, per-Hypothesis `transition_ordinal`, assigned by the trusted writer in the exact semantic transition order while the Team/Hypothesis locks are held. Replay order is `(team_revision, transition_ordinal)`; UUID/record ID is not a semantic tie-breaker. Enforce uniqueness on `(hypothesis_id, team_revision, transition_ordinal)` and reject gaps, duplicate ordinals, or a transition whose `from_confidence` does not equal the preceding reconstructed band. The ordinal is transaction-local ordering metadata, not a wall-clock surrogate. A single transition may use ordinal 1; multiple transitions in one transaction use 1..N in the order actually applied.
- Team revision and epoch-scoped non-decreasing clock are Kernel-owned coordination metadata, not new worker/Task allowed_writes. The typed Task creator and trusted Kernel commit path update them under the Team lock in the same transaction as the corresponding request/business writes; model/worker code cannot write Team or choose a revision/time value.

This is an explicit schema/design cost, not an assertion that the current schema already provides it. If a smaller database-enforced mechanism proves the same non-decreasing clock and serialized history watermark, substitute it with evidence before freeze. Do not fall back to wall-clock-only ordering.

- The creator obtains both values from PostgreSQL only after it owns the Team lock; callers and models cannot supply or override them. Hold the lock through Task/request Event commit.
- Persist exact UTC precision and immutable request fields. The request record needs a database-enforced update/delete guard; if Event does not provide that property, add the smallest guard required.
- Every Hypothesis decision, retry, and interrupted recovery uses the exact persisted as_of, Team revision watermark, epoch, and history manifest. Execution never recomputes them.
- The deterministic Task identity excludes as_of; replay loads and validates the winning Task request and reuses all original pins.
- Provide a test-only deterministic database-clock seam. Production callers must not gain a caller-controlled timestamp parameter.
- A record with a Team revision above the Task watermark is outside that Task's historical view, even if its wall-clock timestamp is earlier. Never clamp or silently include it.

Replay is reconstruction of the original decision. The database-captured instant measures elapsed time; the Team revision establishes serialized history membership.

### 4.3 Historical evidence is authoritative; current-state fields are only accelerators

**Decision proposed:** reconstruct evidence age from immutable accepted evidence history. Hypothesis.last_touched_at is a mutable current-state cache/prefilter, not the authority for a past decay decision. Accepted supporting or challenging EvidenceLinks are the authoritative evidence-touch records. An accepted touch resets evidence age even if confidence does not change.

**Source-backed history gap:** the existing world-memory commit path uses application datetime.now(timezone.utc) for committed_at and stamps Hypothesis, EvidenceLink/ConfidenceChange, and Events with it. ORM server defaults on other insert paths use PostgreSQL now() (transaction-start time). Neither is a database-captured post-lock acceptance instant. The current Hypothesis creation path sets mutable confidence='low' and records confidence='low' in the immutable hypothesis_created Event, but creates no initial ConfidenceChange row. The Event is the only existing immutable record of the initial band; its timestamp is not a reliable database ordering key.

For new accepted evidence touches and confidence transitions, persist the Team revision, active epoch ID, and one database-captured epoch-scoped non-decreasing acceptance/transition instant after acquiring the Team lock. The same values must appear on the history row and its Task-attributed Event. Do not compare instants across epochs or treat existing created_at values as exact serialized acceptance times.

**Required compatibility prerequisite:** the current supported Hypothesis evidence/confidence writer is WorldMemoryCommitService. It currently uses application-captured committed_at and does not populate a Team history revision. Before RW-5 decay can execute, this existing writer must be narrowly adapted to increment the Team revision once per accepted commit, obtain the current epoch-scoped non-decreasing database clock after the required Task → Team → clock-health singleton (FOR SHARE) → Thread → Hypothesis locks, and persist the same revision/epoch/epoch-scoped instant on Hypothesis, EvidenceLink, ConfidenceChange, and their Task-attributed Events. A replay that reuses an existing committed result must not increment the revision or rewrite history. This is a required history-writer compatibility slice, not the separate global before_flush guard retrofit. It touches a shared RW3.4 path and needs its own explicit scope/review against RW-REC-01, RW-REPLAY-01, and RW-RP-01. Until it is implemented and proven, RW-5 may not treat new Hypothesis history as revision-authoritative or run decay Tasks.

**Epoch bootstrap ownership is explicit:** the initial RW-5 epoch is created only by a dedicated, trusted Kernel/application epoch-transition operation under explicit Operator authorization. This is the same narrow transition boundary that will later handle policy/algorithm epoch changes and clock-incident recovery; it is not the typed `apply_decay` Task creator, TaskRuntime, a worker, or a scheduler. In one transaction it acquires the Team `FOR NO KEY UPDATE` lock followed by the clock-health singleton `FOR SHARE` lock, validates the current clock-health generation, captures the Team revision and validated epoch-origin instant, creates exactly one immutable genesis epoch, creates the complete baseline set for every Hypothesis whose canonical lifecycle status is `active` at the epoch's serialized Team-revision cutoff (excluding `superseded` and `rejected` Hypotheses), and activates the epoch. Task creation uses the same Team lock and may admit decay only after it observes that complete active epoch. A database-enforced unique genesis identity (one genesis epoch per Team) and unique `(epoch_id, hypothesis_id)` baseline identity arbitrate duplicates; concurrent bootstrap attempts load and validate the winning complete epoch and never create a second baseline set. If the trusted transition operation, complete baseline set, or explicit authorization is absent, initial activation is unsupported and decay remains disabled/deferred for that Team. No Task creator may synthesize or repair epoch baselines.

**Decay population is active-Hypothesis-only:** at each epoch/bootstrap or successor-epoch transition, the in-scope population is exactly the same-Team Hypotheses whose canonical lifecycle status is `active` at the serialized Team-revision cutoff. Create epoch baselines only for that population. `superseded` and `rejected` Hypotheses are excluded from the epoch baseline set, Task manifest, evidence-age evaluation, and all decay writes; their existing history remains immutable and available for provenance/reconstruction. A Hypothesis created later in the epoch enters the population through its immutable creation Event and current-epoch baseline/anchor rules, and is included in a Task manifest only if it is `active` at that Task's Team-revision cutoff.

At execution, revalidate lifecycle status under the canonical locks. If a manifest member is no longer `active`, do not decay it: record the stable per-Hypothesis skip reason `hypothesis_not_active` and continue only with other still-eligible active members. Unknown or malformed lifecycle states are integrity failures and abort the atomic Task transaction. The operation never changes lifecycle status. The complete Task manifest is the canonical, deterministically ordered set of active Hypotheses at its pinned cutoff; it must not include superseded/rejected rows or silently omit an active row. Manifest bounds apply to this complete active population, and overflow fails Task creation rather than truncating it.

**Initial state and legacy cutover are mandatory:**

- For a Hypothesis created after the new epoch begins, persist its initial confidence band (currently low) in the immutable creation Event together with its current epoch ID/version, Team revision, and canonical acceptance instant. A new initial ConfidenceChange row is not required if the immutable creation Event is sufficient and its contract is enforced.
- At first RW-5 activation, and at every later decay-epoch boundary (including clock-incident recovery and TeamPolicy/decay-algorithm version changes), create an immutable per-Hypothesis epoch baseline for every active Hypothesis in the serialized transition population: current confidence band, epoch ID/version, baseline Team revision, epoch-scoped non-decreasing database baseline instant, and the last eligible EvidenceLink ID and ConfidenceChange ID included as history watermarks. Superseded and rejected Hypotheses receive no decay baseline. **The new epoch baseline instant is the decay-age anchor for all evidence accepted before that epoch**, regardless of any legacy or prior-epoch EvidenceLink timestamps. Preserve those prior EvidenceLink IDs and ConfidenceChange IDs for provenance/reconstruction only; never compare their timestamps with the new epoch clock or use them to calculate elapsed decay windows. Only a newly accepted eligible EvidenceLink in the current epoch may replace the epoch-baseline anchor. Do not retroactively decay legacy time or infer a low-confidence interval from mutable current state.
- **All-or-nothing active-population completeness:** if any active Hypothesis cannot be reconciled with immutable confidence history or cannot receive a valid baseline under the Team lock, epoch bootstrap/successor transition fails atomically with stable reason `decay_epoch_baseline_incomplete`; no partial baseline set or active epoch is committed. For an already active epoch, if any active Hypothesis cannot be represented completely in a Task manifest, reject Task creation with stable reason `decay_manifest_incomplete`; do not create a partial Task/request Event, omit the Hypothesis, or insert a fabricated/deferred placeholder. Do not guess an initial band. This preserves the invariant that every admitted Task manifest is the complete active population at its pinned Team-revision cutoff.
- Every Task request pins the epoch ID/version and a bounded, canonical per-Hypothesis history-watermark manifest containing exactly the active Hypotheses at the Task's serialized Team-revision cutoff: Hypothesis ID, baseline reference/hash, last eligible EvidenceLink ID, last ConfidenceChange ID, Team revision, reconstructed confidence band, and the evidence-age anchor identity/instant. The complete canonical manifest bytes must be retained either directly in the immutable Task request or in a durable immutable content-addressed manifest record referenced by that request. In the latter case, persist both the immutable reference and its content hash, and prove that the referenced bytes remain retrievable and hash-valid for the full Task/recovery retention period. A bare hash without retrievable manifest content is invalid. If the manifest exceeds the configured bound, reject Task creation with a stable overflow reason and admit no partial Task/request Event; do not truncate it. The canonical Task request fingerprint binds as_of, Team revision watermark, epoch ID/version, policy/algorithm versions, schema/manifest version, and the full manifest content hash.
- At execution, after acquiring the canonical locks, compare each manifest member's current eligible history and lifecycle status against its pinned manifest. A newer supporting/challenging EvidenceLink after the Task watermark resets the baseline and makes that Hypothesis ineligible at the older `as_of`; record a stable per-Hypothesis skip reason and allow other still-valid members to proceed. If a manifest member is now `superseded` or `rejected`, skip only that member with `hypothesis_not_active`; an unknown lifecycle value is an integrity failure. In contrast, any newer ConfidenceChange, mismatch between reconstructed history and the mutable confidence projection, or advanced Team decay epoch invalidates the Task's pinned confidence decision: abort the entire Task transaction, including all otherwise-valid members, and let TaskRuntime own retry/recovery. Never partially commit a batch whose confidence history is stale or inconsistent. Unrelated Team revisions do not invalidate a Hypothesis when its own relevant history is unchanged. A Task from a superseded epoch must never commit under the old policy.
- A new TeamPolicy version or decay-algorithm version starts a new epoch at an explicit Team revision and baseline instant, with a new immutable per-Hypothesis baseline for every Hypothesis whose canonical lifecycle status is `active` at the transition's serialized Team-revision cutoff; `superseded` and `rejected` Hypotheses are excluded. That baseline instant supersedes every pre-epoch EvidenceLink timestamp as the decay-age anchor; prior EvidenceLink IDs remain only in the baseline's history-watermark/provenance fields. There is no retroactive catch-up across policy/algorithm epochs. Only a newly accepted eligible EvidenceLink in the new epoch replaces the baseline anchor. Include epoch ID/version, policy version, algorithm version, canonical evidence-touch identity, and window ordinal in the cross-Task decay idempotency key. This prevents a changed window definition from reusing or suppressing an old epoch's step.

Legacy EvidenceLink/ConfidenceChange rows without trustworthy Team revision and post-lock timestamps are covered only by the one-time conservative baseline. No historical catch-up is inferred from their transaction-start or application timestamps.

ConfidenceChange history is authoritative for the confidence band as well as attribution. Reconstruct the band's value by replaying ConfidenceChanges after the immutable creation/epoch baseline in Team revision order; the mutable Hypothesis.confidence column is only a current-state cache and must equal the replayed result under lock. A mismatch is an integrity failure that aborts the entire Task transaction; it is never a per-Hypothesis skip or permission to trust the mutable value. The Task's pinned manifest records the last ConfidenceChange ID and the reconstructed band. Before commit, any newer ConfidenceChange after that watermark makes the old decision stale and prevents it from overwriting the newer band.

**Confidence history and current-state projection are one Kernel-owned atomic write.** For every actual decay transition, the same TaskRuntime/Kernel transaction must (1) append exactly one immutable, Task-attributed ConfidenceChange with the next valid `(team_revision, transition_ordinal)`, and (2) update the corresponding `Hypothesis.confidence` projection to that row's `to_confidence`. The update is performed by trusted application/Kernel code under the canonical Hypothesis lock; it is not a worker-authored proposal and does not grant model code direct Hypothesis write authority. The bounded `apply_decay` operation therefore has an explicit Kernel-managed Hypothesis confidence-projection side effect in addition to its ConfidenceChange write. Both records must be validated against the replayed prior band and committed or rolled back together with the Task summary Event, Outcome, and terminal Task state. A failed flush, constraint, Event write, or terminalization leaves neither the new ConfidenceChange nor the changed Hypothesis projection committed. After commit, replayed history and the mutable projection must agree exactly. No-op lowest-band windows create neither row nor projection update.

**No-new-column is not a freeze assumption.** The epoch baseline, Team revision, and non-decreasing clock need a database-enforced representation. Existing EvidenceLink/ConfidenceChange history may be retained only if property/replay tests prove exact reconstruction across touches with and without confidence change, same-time distinct touches, duplicate replay, transitions into/out of low, catch-up, and evidence arriving after a Task cutoff. Add the smallest immutable field/table needed if those proofs fail; do not preserve a no-migration assumption at the expense of correctness.

A new temporal EvidenceLink index is not assumed. Measure bounded history queries and query plans on a representative disposable PostgreSQL fixture. Add the smallest index only if measured cardinality/latency or bounded-work requirements demand it.

**Window semantics:** use half-open elapsed windows with an inclusive due boundary:

due(k) iff as_of >= anchor + k * W

Use integer/microsecond arithmetic over timezone-aware UTC instants. The anchor is the latest accepted supporting/challenging EvidenceLink touch included in the Task's pinned Team revision and Hypothesis manifest. Decay itself never changes the anchor. When at least one eligible EvidenceLink accepted in the current decay epoch exists, the anchor identity is that canonical current-epoch EvidenceLink ID and its database-captured, post-Team-lock acceptance instant (the latest eligible current-epoch touch under the pinned Team-revision cutoff). A pre-epoch EvidenceLink is never an elapsed-time anchor in the current epoch, even when it is the latest historical EvidenceLink; its ID may remain in the baseline manifest as a history watermark/provenance reference only. When no eligible current-epoch EvidenceLink exists, the anchor is the immutable current-epoch baseline: for a Hypothesis created in the current epoch, use the immutable `hypothesis_created` Event ID and its database-captured acceptance instant; for a Hypothesis carried into this epoch, use its immutable per-Hypothesis epoch-baseline record ID and baseline instant. Never use a mutable `last_touched_at`, a transaction-start timestamp, or a guessed historical timestamp as this fallback.

The first eligible EvidenceLink accepted in the current epoch replaces that epoch's creation/baseline anchor and starts a fresh window sequence at that touch's acceptance instant. Evidence accepted in a prior epoch never replaces a later epoch's baseline anchor. The canonical evidence-age identity is a typed pair `(anchor_kind, anchor_id)` (`evidence_link`, `hypothesis_created_event`, or `epoch_baseline`) plus the pinned anchor instant; include that identity in the cross-Task decay idempotency key. Thus a no-evidence baseline and a first-evidence touch cannot collide or suppress one another. Anchor availability is part of complete-manifest validity, not a per-Hypothesis execution skip: if an active Hypothesis has neither a trustworthy immutable creation Event nor a valid epoch-baseline record at Task creation, reject the entire Task creation with stable reason `decay_anchor_unavailable` before inserting the Task row, request Event, or any partial manifest. This anchor-specific reason takes precedence over the broader `decay_manifest_incomplete` reason; other missing or unreconstructable manifest/history components use `decay_manifest_incomplete`. After Task creation, if the exact pinned anchor ID/instant is missing, corrupt, or cannot be verified at execution, treat it as a batch integrity failure and abort the entire Task transaction. Do not defer/skip only that Hypothesis or commit other members. TaskRuntime owns the resulting retry/recovery/terminalization; no success Event or Outcome may be committed for the aborted business transaction.

Catch up one actual confidence-band transition per elapsed window, in ordinal order; write one ConfidenceChange per actual transition, with no no-op rows after the lowest band. The same Task/replay must not apply a window twice. A deterministic, versioned key identifies (team_id, hypothesis_id, epoch_id, policy_version, algorithm_version, anchor_kind, anchor_id, window ordinal), and a database uniqueness constraint must arbitrate duplicate application across different Tasks.

### 4.4 Confidence transition and policy semantics

**Frozen first-release vocabulary and precedence:**

- `decay_window` is a required, strictly positive finite duration in the effective TeamPolicy. The selected immutable TeamPolicy is the sole runtime source; any pack-provided value must already have been resolved into that published policy. RW-5 does not merge pack and Team overrides at execution, infer a missing value, or introduce another precedence layer. Missing, malformed, zero, negative, non-finite, or unsupported duration values fail closed.
- `decay_action` has one accepted first-release semantic: lower confidence by exactly one band per elapsed `decay_window`. The Kernel default is this action. A supplied action is accepted only if it expresses that exact behavior; unknown actions and pack overrides that change the transition behavior are rejected. The legacy domain description of dormancy is explicitly excluded from this first-release action and cannot be enabled through policy.
- The ordered confidence bands are `high → moderate → low`. One elapsed window causes at most one actual downward transition in that order; multiple elapsed windows apply one transition per window in sequence, stopping at `low`. `low → low` is a no-op: no ConfidenceChange and no Hypothesis projection update. No upward transition is permitted by decay.
- The action never rejects, supersedes, deletes, or otherwise changes Hypothesis lifecycle status. It never updates `last_touched_at` or Thread lifecycle/activity timestamps.
- The effective `decay_window`, accepted `decay_action` semantic, and algorithm version are pinned in the immutable Task request. A replay uses those exact pins and cannot adopt a newer policy midway through catch-up.
- The absence of a decay parser in `core/policy.py` is a source gap, not permission to add a generic policy framework. Implement only a narrow parser/validator for these two consumed values; fail closed on unsupported vocabulary. No implicit duration default is defined by this contract.

Every actual transition creates exactly one ConfidenceChange with `cause_kind="decay"`, the current decay Task attribution, the deterministic per-window idempotency key, and the next per-Hypothesis transition ordinal. In the same transaction, trusted Kernel code updates `Hypothesis.confidence` to the recorded `to_confidence` as specified above.

### 4.5 Dormancy is out of scope until D6 recovery exists

**RW-5 first release performs confidence decay only. It does not transition Threads to `dormant`.**

Dormancy is an irreversible lifecycle transition for the current delivery sequence: it can make a Thread unavailable to the first RW-4 matching path, while the authorized reactivation/recovery path is not yet implemented. The non-vacuous rule (“at least one active Hypothesis, and every active Hypothesis is low and beyond the accepted inactivity threshold”) is not sufficient by itself. A lifecycle transition must not ship before its recovery path exists.

- RW-5 must not change Thread status or Thread lifecycle/activity timestamps and must not emit a dormancy Event.
- Do not add dormancy as an optional policy flag in the first RW-5 release.
- Dormancy requires D6 acceptance, a durable RW-4 reactivation path, and an explicit recovery/reconsideration behavior for decay-first and triage-first outcomes.
- If dormancy is later authorized, reconstruct low-confidence age from accepted evidence and ConfidenceChange history as described above; never infer it solely from mutable current-state fields.

This is a hard scope boundary, not a deferred implementation detail within RW-5.

### 4.6 Shared lock order and database-enforced concurrency

**Proposed canonical lock order and modes:**

1. Lock the current Task row with FOR UPDATE when a Task exists; validate running status, exact attempt number/start, immutable request, policy pin, and absence of a newer attempt. Hold this lock through commit/rollback.
2. Lock the Team row with FOR NO KEY UPDATE as the per-Team writer serialization point.
3. Lock the database-scoped clock-health singleton row with a shared row lock (FOR SHARE). Validate the current health generation/source and fresh independent sample while holding it; retain the lock through commit/rollback. The health monitor latches or changes health state only while holding the corresponding exclusive row lock (FOR UPDATE), and never acquires a Team lock.
4. Lock affected Thread rows one at a time in ascending canonical ID order with FOR NO KEY UPDATE.
5. Lock affected Hypothesis rows one at a time in ascending canonical ID order with FOR NO KEY UPDATE.
6. Re-read and revalidate Team ownership, Thread/Hypothesis membership and lifecycle, current history watermark, policy/epoch pin, clock-health generation/source/freshness, and current-attempt preconditions under those locks.
7. Only then flush child EvidenceLink/ConfidenceChange rows and Task-attributed Events through the accepted TaskRuntime/Kernel transaction boundary.

The lock-mode choice is deliberate. PostgreSQL foreign-key checks take FOR KEY SHARE protection on referenced parent rows. FOR UPDATE conflicts with that protection and can deadlock with a child-first writer; FOR NO KEY UPDATE conflicts with another writer's FOR NO KEY UPDATE (so it still serializes same-Team writers) while remaining compatible with FK FOR KEY SHARE. The clock-health singleton uses FOR SHARE for participating writers/readers and FOR UPDATE for the health monitor's state changes; the shared lock prevents a health-generation/status change between validation and commit. The monitor takes only the singleton lock and never a Team lock, so there is no reverse singleton → Team edge. The disposable spike in tests/test_rw5_postgres_lock_spike.py tests the existing PostgreSQL FK/Team-lock mechanics; it does not yet prove this clock-health lock protocol. Task rows remain FOR UPDATE because Task attempt/lifecycle fencing is an update boundary. Do not use a set-based ORDER BY ... FOR UPDATE as proof of lock acquisition order: the canonical helper must acquire each Thread/Hypothesis row individually in sorted ID order.

The Task creator has no Task row to lock yet. It acquires Team FOR NO KEY UPDATE, then the clock-health singleton FOR SHARE, validates health, captures as_of and the Team revision watermark, and inserts Task + request Event in that same transaction. It must not discover/lock a Thread or Hypothesis before acquiring Team.

For decay execution, the order is Task FOR UPDATE → Team FOR NO KEY UPDATE → clock-health singleton FOR SHARE → sorted Thread rows → sorted Hypothesis rows. For a history-writing transaction or epoch transition with no Task row, acquire Team → clock-health singleton → sorted Thread rows (if affected) → sorted Hypothesis rows (if affected). Every transaction that validates clock health or advances an epoch clock follows this order. The health monitor acquires only the singleton FOR UPDATE lock, commits its generation/status update, and never requests Team, Thread, or Hypothesis locks. All shared/exclusive singleton locks are held until transaction completion.

**One canonical helper is mandatory for new RW-5/RW-4 writers.** No per-writer equivalent lock implementations. The helper owns Task fencing (when a Task exists), Team lock, clock-health singleton lock, sorted Thread/Hypothesis locks, the session lock registry, and under-lock revalidation. Candidate discovery may be read-only before locking; after Team/health/Thread locks, reload the candidate and the `active` Hypothesis set. If a candidate moved or membership changed, restart discovery or defer; never act on stale discovery.

The session lock registry records exact Task/Team/clock-health/Thread/Hypothesis locks held by the current SQLAlchemy Session, including lock mode for the singleton. A before_flush guard checks protected ORM inserts/updates/deletes against that registry for new RW-5/RW-4 paths only. Acquire locks inside session.no_autoflush and do not stage child rows before the helper completes, so autoflush cannot take FK locks before the intended order. The guard must reject a Hypothesis thread_id move through ordinary updates; a future move needs a separately specified operation.

**Protected-write matrix (Task lock is required for both child rows because both have Task foreign keys):**

| Operation | Required locks before ORM flush |
|---|---|
| Create apply_decay Task/request | Team → clock-health (FOR SHARE) |
| Update Thread | Task → Team → clock-health (FOR SHARE) → Thread |
| Insert Hypothesis | Task → Team → clock-health (FOR SHARE) → Thread |
| Update Hypothesis | Task → Team → clock-health (FOR SHARE) → Thread → Hypothesis |
| Insert Hypothesis-subject EvidenceLink (originating_task_id) | Task → Team → clock-health (FOR SHARE) → Thread → Hypothesis |
| Insert ConfidenceChange (created_by_task_id) | Task → Team → clock-health (FOR SHARE) → Thread → Hypothesis |
| Advance epoch clock / create or recover decay epoch (no Task) | Team → clock-health (FOR SHARE) → sorted Hypotheses |
| Latch/update clock-health incident | clock-health (FOR UPDATE) only |

EvidenceLink rows with subject_kind='evaluation' are not Hypothesis evidence-touch writers and are outside this RW-5 protected-write matrix. Thread creation is not part of RW-5; any later Thread creator must serialize on Team and use a database uniqueness constraint for canonical creation identity because no Thread row exists to lock.

**Scope of enforcement and writer inventory:**

- The helper and lock registry/guard are mandatory for every new RW-5/RW-4 writer introduced under this contract. The guard is activated only for those new-path Sessions; do not retrofit a global enforcing before_flush listener onto all existing production sessions as part of RW-5 freeze.
- The generic existing-writer guard retrofit is a separately gated follow-up: instrument the current production session factory in log-only mode, run the full suite and supported integration paths, classify every protected-table write that lacks registry evidence, then remediate and switch to enforcement in a later reviewed step. The maintained full writer inventory must be generated/updated from this run, not asserted from memory or this bounded source audit. This follow-up is distinct from the required narrow WorldMemoryCommitService revision/clock adaptation above.
- before_flush does not intercept raw SQL, SQLAlchemy Core bulk DML, or other database clients. New RW-5/RW-4 protected-write paths must not use Core bulk DML or raw SQL for protected rows unless a separately reviewed database function enforces the same lock/identity contract. Database-role/privilege enforcement for scripts and external writers is a named deployment residual, not part of this RW-5 code contract. Do not claim the ORM guard is a complete database security boundary.
- The bounded source audit found the current WorldMemoryCommitService locks Task → Team → Thread → Hypothesis using FOR UPDATE, then writes Hypothesis EvidenceLinks and ConfidenceChanges; it is the current relevant writer path. Its timestamp/revision adaptation is a required precondition before decay execution, separately scoped and reviewed as shared RW3.4-adjacent work. The generic log-only guard retrofit remains a separate follow-up. The new FOR NO KEY UPDATE helper serializes against the existing Team FOR UPDATE lock; FK compatibility improvement applies to the new helper and any writer later migrated to it.

The Team lock intentionally serializes writes for one Team. Measure contention before considering a narrower scheme. A bounded lock timeout is required. PostgreSQL deadlock 40P01 and lock-not-available/lock-timeout 55P03 are retryable Task failures after rolling back the entire transaction. Do not swallow them as per-Hypothesis skips. Application prechecks improve diagnostics; database uniqueness/constraints and row locks remain the concurrency authority.

### 4.7 Decay/triage race outcomes

The exclusive Team lock serializes decay and triage writers for the same Team. Each operation reloads and revalidates canonical rows and accepted history after acquiring it.

- **Triage commits first:** the later decay operation observes the newer EvidenceLink/revision under the Team and Hypothesis locks. Because the touch is after the Task's pinned history watermark, that Hypothesis is skipped as not due at the older `as_of`; the Task never writes a stale confidence decrement over the newer evidence.
- **A newer confidence transition or epoch commits first:** a decay Task with an older per-Hypothesis manifest or superseded epoch defers rather than overwriting the new confidence state or applying an old policy window.
- **Decay commits first:** triage observes the committed confidence state. Before D6 and a durable reactivation/recovery path exist, dormant-Thread behavior is not reachable because RW-5 does not create dormant Threads.
- **After D6:** a separately authorized reactivation path must validate current Team, Thread, Hypothesis, and evidence state under the same lock order and emit at most one reactivation Event. It must also define how decay-first state is reconsidered; merely changing `dormant → active` is not enough.
- A losing concurrent/replayed request loads or validates the canonical committed result; it cannot append a duplicate ConfidenceChange or lifecycle Event.

Prove both race orders with disposable PostgreSQL. Unit tests that mock away row locks do not prove serialization.

### 4.8 Task transaction, recovery, and per-Hypothesis failures

**Atomicity is a required design proof, not an assumption about the current APIs.** The existing WorldMemoryCommitService.commit_model() opens its own transaction, while TaskRuntime.finalize() opens a separate transaction. commit_model_in_session() provides a possible shared-session seam, but the current finalization API does not itself prove that business writes, summary Event, Outcome, and terminal Task state can commit atomically. A TaskRuntime-owned finalize-in-session extension may touch shared RW3.4 code; it is not an incidental RW-5 refactor and is not authorized by this proposal.

Before implementation, separately review the exact shared-runtime change against the seven RW3.4 residuals. The current impact map is: RW-REC-01 (Task/attempt lock and fencing cases), RW-REPLAY-01 (atomic write/replay behavior), and RW-RP-01 (unknown-commit/repeated recovery) are directly touched and require targeted RW-5 proof while remaining PARTIAL outside that proof. RW-CTX-06 is not touched unless Context identity/recovery code changes; RW-RT-02 is not touched unless the 45s/60s timing contract changes; RW-REQ-01 and RW-POL-01 remain external host-authentication and policy-publisher boundaries. No RW3.4 row is closed by this mapping. If the required TaskRuntime change exceeds this narrow boundary, stop for a separate RW3.4 impact review and explicit authorization.

The accepted target is one transaction that commits:

- all eligible decay ConfidenceChanges;
- the single deterministic summary Event;
- the Task Outcome; and
- the terminal Task state.

Task fencing is mandatory: lock Task FOR UPDATE, validate status='running', exact current attempt and its start record, immutable request/fingerprint and policy/epoch pins, and absence of a newer attempt; hold the lock through the entire transaction. Use PostgreSQL READ COMMITTED only after the Team-lock coverage contract is satisfied: every supported writer that changes relevant history must acquire the same Team serialization lock before mutation, and every new RW-5/RW-4 writer must use the canonical helper. After waiting for Team, perform fresh statements to reload history and membership under the lock. Do not use REPEATABLE READ with a snapshot established before waiting for Team; if a future design chooses SERIALIZABLE, classify 40001 as a whole-transaction retry.

Bound batch size, transaction duration, and lock duration. Deterministic ineligibility may be skipped only with an explicit stable reason in the summary. Integrity violations, ownership conflicts, stale attempts, malformed policy, lock timeout/deadlock, and infrastructure/transaction errors abort and roll back the entire transaction; do not swallow them as per-Hypothesis skips.

**Unknown commit resolution:** if the connection is lost during commit, reconnect and inspect only the atomic terminal marker: Task terminal status plus its matching terminal Outcome. If both agree with the pinned Task/attempt/result, treat the transaction as committed. If neither exists, let TaskRuntime's existing retry/recovery policy proceed. If one exists without the other or the pair conflicts, fail closed as inconsistent. Do not re-query/reconstruct the expected business-write set in recovery; the same transaction makes those writes atomic, and tests verify their presence/absence. Database uniqueness on the decay-step identity remains the second line of defense against duplicate writes.

Inject failures before writes, after business writes, before summary Event, and before terminal Task state. Each failure must prove rollback of business rows, Event, Outcome, and Task state. Do not add savepoints unless an accepted requirement demonstrates that individual Hypothesis failures must be isolated.

Classify PostgreSQL errors after rolling back the entire transaction: 40P01 deadlock and 55P03 lock timeout/not-available are retryable; 40001 is retryable only if SERIALIZABLE is deliberately selected; 57014 statement cancellation/timeout is separately classified and is not automatically a lock retry. Never continue in a failed transaction or commit a partial batch.

If a clean single-transaction TaskRuntime path cannot be implemented, stop. A separate durable marker/receipt plus recovery protocol requires a new design and explicit review; do not claim atomicity while using two transactions. TaskRuntime remains the only lifecycle and interrupted-recovery authority.

### 4.9 Bounded work

The Team batch must have explicit maximum Hypothesis count, maximum EvidenceLink-history rows examined, and a bounded transaction/lock duration. Query only the canonical Team scope; detect overflow before mutation and fail/defer the Task rather than silently truncating a candidate or history set. Measure query plans and cardinality on a representative disposable PostgreSQL fixture. Any required pagination must preserve one immutable `as_of`, one pinned policy, and deterministic ordering across the entire Task. The summary Event reports deterministic counts and explicit overflow/failure outcome without leaking unbounded payloads.

### 4.10 RW-5 first-release acceptance boundary

RW-5 first release means: typed idempotent Task creation; database-captured immutable request `as_of`; pinned policy; history-authoritative confidence decay; database-enforced uniqueness and immutable records; shared lock-order proof; atomic TaskRuntime/Kernel business commit and terminalization; bounded work; deterministic retry/replay. It does **not** include periodic scheduling (RW5-P), Thread dormancy, reactivation, or autonomous lifecycle management. RW5-P remains required before foundation exit/R8 can claim periodic decay is operational.

## 5. Schema and migration posture

Prefer the existing Thread, Hypothesis, ConfidenceChange, Task, and Event records. In particular:

- Do not add a dedicated `decay_task_id` column merely to duplicate the generic Task attribution already present on ConfidenceChange.
- Do not use `last_touched_at` as historical authority. Avoid a new age/streak column only if accepted EvidenceLink and ConfidenceChange history—with database-captured post-Team-lock acceptance/transition instants—reconstructs the exact baseline and streak under property/replay tests, while `last_touched_at` is verified as a cache. Add the smallest immutable timestamp/touch identity field if existing records cannot safely carry that information.
- Expect a minimal partial unique index for cross-Task decay-step idempotency unless an equally strong database-enforced alternative is demonstrated; the current Task-scoped unique constraint is not sufficient by itself.
- Use the existing Task UUID primary key for deterministic Task-creation identity if golden-vector and concurrent-creation tests validate the proposed UUIDv5 scheme; add no generic idempotency column by default.
- Do not add Thread embeddings, new Domain policy subsystems, or a scheduler/runtime as part of RW-5.
- Expect a minimal migration for Team history revision and per-epoch non-decreasing clock state, immutable per-Hypothesis epoch baselines, and the revision/acceptance metadata needed to replay relevant Hypothesis/EvidenceLink/ConfidenceChange history. The following logical representation is the proposed freeze baseline; implementation may rename or combine storage only if it preserves every listed invariant and supplies equivalent database enforcement.


### 5.1 Minimum logical representation and database constraints

The proposal selects the following smallest understandable logical model. These are contract-level records/fields, not authorization to implement them in this PR:

| Record | Required durable state |
|---|---|
| Team | `world_memory_revision BIGINT NOT NULL`, incremented exactly once by each accepted transaction that changes relevant Hypothesis/history state. The Team row remains the serialization point. |
| DecayEpoch | Immutable identity, `team_id`, per-Team epoch ordinal, predecessor (nullable for genesis), transition kind/key, policy and algorithm versions, clock-health generation/source/configuration pins, epoch origin instant, and the mutable non-decreasing `last_clock_at` field. Status identifies the single active epoch. |
| DecayEpochBaseline | One immutable row per `(epoch_id, hypothesis_id)`, carrying Team identity, baseline confidence, baseline Team revision, baseline instant, typed anchor kind/ID/instant, and last included EvidenceLink and ConfidenceChange IDs. It exists only for Hypotheses active at the serialized epoch cutoff. |
| Hypothesis creation Event | Immutable initial confidence band, Team revision, epoch ID, and database-captured acceptance instant. This is the initial confidence baseline for Hypotheses created inside an epoch. |
| Relevant EvidenceLink | Team revision, epoch ID, and database-captured post-lock acceptance instant for eligible Hypothesis-subject support/challenge evidence. |
| ConfidenceChange | Team revision, epoch ID, database-captured transition instant, positive per-Hypothesis `transition_ordinal`, and the existing Task attribution/idempotency data. |
| ClockHealth singleton | Exactly one database-scoped row containing singleton key, monotonic health generation, healthy/incident status, source identity, last sample ID, source/configuration version, and the source-native monotonic sample observation/token. Sample age is evaluated only against that same independent monotonic source; a database-wall-clock expiry is not authoritative. |
| Task request | Immutable epoch ID, epoch-scoped `as_of`, Team revision watermark, policy/algorithm versions, manifest schema version, and the complete canonical manifest content (or a durable immutable content-addressed record with both reference and hash). The Task fingerprint binds all these values. |

Required database arbitration/enforcement:

- `UNIQUE(team_id, epoch_ordinal)`; a partial unique index permits at most one active epoch per Team; a separate partial unique index permits at most one genesis epoch per Team.
- A unique per-Team transition identity, such as `UNIQUE(team_id, transition_key)`, prevents concurrent retries from creating duplicate successor epochs. The key canonically binds predecessor epoch, transition kind, and target policy/algorithm version.
- `UNIQUE(epoch_id, hypothesis_id)` on DecayEpochBaseline, with composite Team-ownership foreign keys (or equivalent constraints) proving that the epoch and Hypothesis belong to the same Team.
- `UNIQUE(hypothesis_id, team_revision, transition_ordinal)` on ConfidenceChange; reject non-positive ordinals and enforce the documented contiguous chain in the trusted writer/replay validator.
- A database unique key for the cross-Task decay step identity: Team, Hypothesis, epoch, policy version, algorithm version, typed anchor kind/ID, and window ordinal. The existing Task-scoped uniqueness is not sufficient.
- The clock-health table enforces its singleton identity (one fixed key only) and monotonic generation updates. Team revision and epoch clock updates occur under the Team lock in the same transaction as the accepted writes; database constraints/triggers must reject invalid backward updates within an epoch.
- Epoch identities, baselines, accepted history metadata, Task request pins, and manifest content are immutable after insertion. Enforce this through database privileges and/or narrowly scoped triggers, not application convention alone. The active-epoch transition and mutable `last_clock_at` must have narrowly defined update rules; ordinary writers cannot edit or delete prior epoch/baseline/history records.
- If the complete manifest is stored in the Task request, the immutable request must retain the full canonical manifest object and its versioned canonicalization rule so the exact bytes and hash can be reproduced. If stored separately, use one immutable manifest row keyed by Task ID with canonical bytes and hash; do not store only a hash or allow mutable external object storage.

The model deliberately avoids a generic temporal framework, generic event store, or a second scheduler. It adds only the epoch/baseline/health state and history metadata required by the stated invariants. If source inspection shows an existing table can hold one of these records without weakening immutability or ownership constraints, reuse it; document the exact constraint that supplies the same guarantee.

## 7. Separate scheduler/host integration gate (RW5-P)

RW5-P is not part of the deterministic decay core. It is a separately gated integration for periodic invocation by a trusted host scheduler.

It must define schedule cadence/time zone, missed-run behavior, per-Team fan-out, idempotent schedule-slot identity, retry/backoff, disabled/inactive Team behavior, observability, and operator controls. The host scheduler may create an `apply_decay` Task through the typed creator; it may not execute the Task or write world memory. No Watch-owned periodic loop, TaskDispatcher expansion, or second runtime is implied.
