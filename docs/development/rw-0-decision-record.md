| RW-D27 | Use 10 control runs and 10 treatment runs for the first newsroom experiment. Isolate run state so experience generated in one run cannot contaminate another run or condition. | RW-D28 | Use three predeclared acceptance gates for the initial newsroom experiment: (1) treatment mean total score exceeds control by at least 10 points out of 100; (2) treatment does not increase critical factual errors, with every critical error in either condition disclosed and examined; and (3) treatment demonstrates claim-level use of retrieved knowledge, not merely improved presentation. Report score distributions, uncertainty, and individual runs; do not characterize 10 runs per condition as statistical proof. | Confirmed |
| RW-D29 | Isolate scored newsroom runs: start each run from the same frozen baseline; expose the same frozen retained-experience snapshot only to treatment runs; prevent experience written by any scored run from being retrieved by another scored run; and keep retrieval/Context processing identical except for treatment snapshot availability. This evaluates the value of access to retained experience, not uncontrolled learning during the experiment. | Confirmed |
| RW-D30 | Use two independent reviewers for every newsroom output. Reviewers receive anonymized outputs without control/treatment labels and score independently before discussing disagreements. Preserve both original scores. Material disagreements must be adjudicated by a third reviewer or resolved through a documented process; retain the original scores and the resolution record. | Confirmed |
| RW-D31 | Trigger formal reviewer-disagreement resolution if (1) total scores differ by more than 10 points out of 100, (2) reviewers disagree on whether a critical factual error occurred, or (3) reviewers disagree on whether a central claim is unsupported or materially misleading. Preserve both original assessments and the adjudication/documented resolution. | Confirmed |
| RW-D32 | Reviewers must have sufficient science/technology literacy and evidence-evaluation ability, but need not be professional journalists. For claim verification, they must be able to inspect the fixed source packet and verify claims against it. For editorial assessment, they must understand scientific communication, uncertainty, and evidence-based reasoning. | Confirmed |
| RW-D33 | Use the same two reviewers for all 20 newsroom outputs. Present anonymized outputs in randomized order and distribute review across balanced batches with breaks to reduce fatigue and condition/order effects. Preserve the presentation order and batch assignment as evaluation metadata. | Confirmed |
| RW-D34 | Before scored evaluation, conduct a separate reviewer-calibration exercise using sample analyses excluded from the 20 experimental runs. Both reviewers independently score the same examples with the frozen rubric, then discuss discrepancies and clarify ambiguous anchors; repeat calibration if needed. Calibration aims for consistent rubric interpretation, not forced agreement on every judgment. | Confirmed |
| RW-D35 | Accept reviewer calibration qualitatively: reviewers must apply the critical-factual-error definition consistently and interpret the 50-point claim-verification and 50-point editorial components consistently, with no unresolved ambiguity in scoring anchors that could materially affect results. Do not impose a numerical inter-rater reliability threshold, because the calibration sample is small and such a threshold could create false confidence. | Confirmed |
| RW-D36 | Define the 50-point claim-verification rubric around four categories: factual accuracy against the source packet; evidence traceability of claims to relevant sources; quotation and attribution accuracy; and numerical and temporal accuracy, including figures, dates, and units. Defer exact point allocations and detailed scoring anchors until the newsroom assignment and source-grounded answer key have been prepared, so the allocation reflects the actual task and evidence rather than being arbitrary. | Confirmed |
| RW-D37 | Define the 50-point editorial-assessment rubric around four categories: interpretation of what the findings mean; significance and why the findings matter without exaggeration; uncertainty and limitations, including the distinction between established findings and open questions; and synthesis that integrates evidence across sources into a coherent analysis rather than merely summarizing sources independently. Defer exact point allocations and detailed scoring anchors until the newsroom assignment and source-grounded answer key have been prepared. | Confirmed |
| RW-D38 | Define a critical factual error as a materially consequential false, unsupported, or misleading claim that changes the reader's understanding of the central finding, its strength, its implications, or the evidence supporting it. Examples include reversing the central finding; presenting correlation as demonstrated causation; inventing or materially altering a result, quotation, or statistic; omitting a limitation in a way that materially changes the conclusion; or attributing a finding to the wrong study, researcher, or source. Minor wording issues and non-material inaccuracies do not qualify. Apply the definition against the frozen source packet and answer key, with examples serving as guidance rather than an exhaustive list. | Confirmed |
| RW-D39 | Count each distinct underlying critical factual error once per output, even if it is repeated within that output; count genuinely different critical errors separately. Report, for each condition, the total number of critical errors and the number of outputs affected. Use these counts when comparing control and treatment for the predeclared critical-error acceptance gate, avoiding inflation from repetition while preserving the prevalence of affected outputs. | Confirmed |
| RW-D40 | Prepare a source-grounded answer key before scored runs, independently of model-generated outputs. For each expected factual claim, record its source and exact location, supported statement, qualifications/limitations, central-or-secondary importance, and known ambiguity or source disagreement. Explicitly identify important facts the packet does not establish, potentially unsupported or misleading claims, and acceptable alternative interpretations. Do not make the key a closed list of approved wording: reviewers may credit novel claims when their underlying factual content is accurate and supported by the frozen packet. Freeze the answer key with the corpus and scored brief before any scored run. | Confirmed |
| RW-D41 | Select the fixed newsroom source corpus using primary-source preference (original research papers, official datasets, and direct institutional publications where available); require each source to contribute relevant evidence; include sources needed to represent important qualifications, limitations, and conflicting findings; preserve exact source files or stable archived versions with retrieval dates and cryptographic hashes; prohibit source additions after freeze for either condition; and record important candidate sources excluded with reasons. Freeze the corpus and its version manifest before scored runs. | Confirmed |
| RW-D42 | Determine source-packet size by evidentiary sufficiency, not a predetermined numerical target. Do not add sources merely to make the packet appear comprehensive. | Confirmed |
| RW-D43 | Select the newsroom story using evidence availability (accessible primary research or equivalent), direct verifiability of important claims against the packet, meaningful interpretive depth (significance, limitations, or uncertainty), bounded scope, and reproducibility through preserved sources. Avoid breaking-news or rapidly changing subjects so the experiment measures retained experience rather than changes in available information. | Confirmed |
| RW-D44 | Freeze the source packet and manifest before finalizing the scored newsroom brief. This prevents the brief from steering source selection toward a desired conclusion. | Confirmed |
| RW-D45 | Use a fixed scored newsroom brief structure: task; intended audience; scope (including what is out of scope); evidence rule (use only the supplied packet and distinguish source-supported findings from interpretation and uncertainty); required elements (central finding, significance, limitations, uncertainty, and comparison of relevant sources); and consistent output format and length limit. | RW-D46 | Use a consistent structured editorial-analysis output for every scored run: headline; central finding; why it matters; evidence and source comparison; limitations and uncertainty; and what remains unknown. | RW-D47 | Apply one common word limit to all 20 scored outputs; choose the exact limit after the story and brief are drafted. Require all material to appear within the defined sections, identify sources consistently by packet IDs, and prohibit extra material outside the required sections. | RW-D48 | Require explicit packet-ID attribution for direct factual claims. | RW-D49 | Count claim-level use of retained knowledge only when a specific output claim is linked to the exact accepted KnowledgeItem version and originating LearningChange; an immutable TaskKnowledgeReference and Context manifest establish that the same version entered that Task's Context; application validation confirms identity, version, eligibility, and Context linkage; and independent reviewers judge whether the knowledge materially supports, qualifies, or informs the claim. | RW-D50 | Treat retained knowledge as materially influencing an output claim when it supports the claim with relevant evidence or reasoning, qualifies it with a material limitation, uncertainty, or condition, or corrects/prevents a misleading conclusion by distinguishing related findings or interpretations. | RW-D51 | For the treatment condition, independently assess all 10 outputs, record each qualifying claim and its retained-knowledge reference, report the number of outputs with at least one independently verified qualifying claim, and separately report unsupported attribution attempts. | RW-D52 | Permit one accepted KnowledgeItem version to materially influence multiple output claims, and permit multiple accepted KnowledgeItem versions to materially influence one output claim. | RW-D57 | Reviewers identify claims from the actual immutable output, not solely from model-supplied claim IDs. Two-reviewer protocol (RW-D30): every output is independently scored by two reviewers who receive anonymized outputs without condition labels. They submit scores before discussion; both original scores are retained. Material disagreements are adjudicated by a third reviewer or resolved using a documented process, with the resolution preserved rather than overwriting the initial assessments.

Reviewer-disagreement triggers (RW-D31): require formal resolution when total scores differ by more than 10/100, reviewers disagree on the presence of a critical factual error, or they disagree on whether a central claim is unsupported or materially misleading. Preserve both initial assessments and the resolution record.

Reviewer qualifications (RW-D32): reviewers need relevant science/technology literacy and evidence-evaluation ability, but need not be professional journalists. Claim verification requires the ability to inspect the fixed source packet and verify claims against it; editorial assessment requires understanding of scientific communication, uncertainty, and evidence-based reasoning.

Reviewer assignment (RW-D33): use the same two reviewers for all 20 outputs. Randomize anonymized presentation order and distribute work across balanced batches with breaks. Preserve order and batch metadata so fatigue and order effects can be examined.

Reviewer calibration (RW-D34): before scored evaluation, both reviewers independently score the same sample analyses excluded from the 20 experimental runs using the frozen rubric. They then discuss discrepancies and clarify ambiguous scoring anchors; repeat calibration if needed. The goal is consistent interpretation, not forced agreement on every judgment.

Calibration acceptance criteria (RW-D35): calibration is accepted when reviewers apply the critical-factual-error definition consistently, interpret both 50-point rubric components consistently, and have no unresolved ambiguity in scoring anchors that could materially affect results. No numerical inter-rater reliability threshold is imposed; the calibration sample is too small for such a threshold to provide meaningful assurance.

Claim-verification rubric structure (RW-D36): the 50-point claim-verification component is organized around factual accuracy against the source packet, evidence traceability, quotation and attribution accuracy, and numerical and temporal accuracy (including figures, dates, and units). Exact point allocations and detailed anchors remain open until the newsroom assignment and source-grounded answer key are prepared, avoiding arbitrary weighting before the actual claims and evidence are known.

Editorial-assessment rubric structure (RW-D37): the 50-point editorial component covers interpretation of findings, significance without exaggeration, uncertainty and limitations, and synthesis across sources into a coherent analysis. Exact point allocations and detailed anchors remain open until the newsroom assignment and source-grounded answer key are prepared.

Critical factual error definition (RW-D38): a critical error is a materially consequential false, unsupported, or misleading claim that changes the reader's understanding of the central finding, its strength, implications, or evidentiary basis. Examples include reversing the central finding; presenting correlation as demonstrated causation; inventing or materially altering a result, quotation, or statistic; omitting a limitation in a materially conclusion-changing way; or misattributing a finding. Minor wording issues and non-material inaccuracies are excluded. Apply the definition against the frozen source packet and answer key; examples are illustrative, not exhaustive.

Critical-error counting and reporting (RW-D39): count each distinct underlying critical factual error once per output, even if repeated; count genuinely different errors separately. For control and treatment separately, report both total critical errors and the number of outputs affected. Compare these counts under the predeclared critical-error acceptance gate.


Source-grounded answer key (RW-D40): prepare the key before scored runs and independently of model-generated outputs. For each expected factual claim, record its source and exact location, supported statement, qualifications/limitations, central-or-secondary importance, and known ambiguity or disagreement between sources. Identify important facts the packet does not establish, potentially unsupported or misleading claims, and acceptable alternative interpretations. The key is not a closed list of approved wording: reviewers may credit novel claims when their underlying factual content is accurate and supported by the frozen packet. Freeze the answer key with the corpus and scored task brief before any scored run.


Material influence categories (RW-D50): reviewers may count retained knowledge as materially influencing a specific output claim when it (1) supports the claim with relevant evidence or reasoning; (2) qualifies the claim with a material limitation, uncertainty, or condition; or (3) corrects or prevents a misleading conclusion by distinguishing related findings or interpretations. Mere topical similarity, a passing mention, or an irrelevant citation does not count.

Claim-use gate minimum (RW-D51): all 10 treatment outputs are assessed independently. Record every qualifying claim and its retained-knowledge reference; report how many outputs contain at least one independently verified qualifying claim; and report unsupported attribution attempts separately. At least one verified qualifying claim across the treatment condition is required to demonstrate that claim-level attribution works. This minimum does not demonstrate consistent use across all runs. Show the full distribution and do not impose an arbitrary percentage threshold in advance.

Many-to-many claim/knowledge attribution (RW-D52): one accepted KnowledgeItem version may materially influence multiple output claims, and multiple accepted KnowledgeItem versions may materially influence one output claim. Record and independently assess each claimed relationship; do not impose a one-to-one mapping.

Ambiguous claim/knowledge attribution (RW-D53): reviewers classify each claimed relationship as (1) qualifying, when it meets a D50 material-influence category; (2) non-qualifying, when documented but not materially influential; or (3) indeterminate, when available evidence is insufficient to decide. Only qualifying relationships count toward the acceptance gate. Preserve indeterminate relationships in reporting rather than silently treating them as successes or failures.

Reviewer disagreement for claim-use attribution (RW-D54): two reviewers independently classify each claimed claim-to-knowledge relationship. Agreement establishes the provisional classification. Disagreement triggers adjudication by a third qualified reviewer; the adjudicated result becomes final, while both original judgments and the disagreement remain recorded.

Claim-use review evidence record (RW-D55): retain, for every reviewed relationship, the output ID and claim ID; exact KnowledgeItem ID and version; originating LearningChange ID; reviewer classification; a concise explanation identifying the specific evidence or reasoning supporting that classification; reviewer identity; and adjudication status where applicable. This explanation records the reviewer’s evidence-based judgment, not a reconstruction of hidden model reasoning.

Claim-use reporting levels (RW-D56): report (1) relationship-level counts for qualifying, non-qualifying, and indeterminate relationships, including adjudicated disagreements; (2) output-level coverage, showing how many of the 10 treatment outputs contain at least one qualifying relationship; and (3) condition-level aggregate results across all 10 treatment outputs, with the full distribution visible. This prevents numerous references concentrated in one output from masking the absence of qualifying use in other outputs.

Claim identification for attribution review (RW-D57): reviewers identify claims from the actual output, not solely from model-supplied claim IDs. Assign each distinct factual or interpretive claim a stable ID within its output. Split compound sentences when their components can be independently evaluated; repeated statements of the same underlying claim are not separate claims. Keep the original output immutable; claim IDs and annotations belong to the review record.

Claim review scope (RW-D58): identify claims by meaning rather than sentence count. Include factual and interpretive assertions about the subject; include headlines and section headings when they make substantive assertions; and include uncertainty statements that assert evidence is limited, conflicting, or insufficient. Exclude purely rhetorical transitions, questions, and stylistic language unless they imply a factual or interpretive assertion.

Independent claim identification and reconciliation (RW-D59): both reviewers independently identify and annotate claims from each immutable output before discussing the output or one another's inventories. They then reconcile differences, including disputed claim boundaries, omitted claims, and possible duplicate identification. Refer unresolved disagreements to a third qualified reviewer. Preserve both original inventories and the reconciled inventory; reconciliation must not overwrite the independent records.

Claim attribution completeness (RW-D60): retain every identified claim in the reconciled inventory regardless of whether any retained-knowledge relationship is attributed to it. Record claimed claim-to-knowledge relationships separately; do not presume that every claim should use retained knowledge. Report mutually exclusive claim counts in three groups: claims with at least one qualifying relationship; claims with one or more attribution attempts but no qualifying relationship (including non-qualifying and/or indeterminate relationships only); and claims with no attribution attempt. An unattributed claim is not a failure: the experiment tests whether retained knowledge is used where relevant, not whether every output claim cites memory. This preserves the complete claim inventory as the reporting denominator without pressuring the model to attach memory references to every claim.

Attribution reference eligibility (RW-D61): a claim-to-knowledge relationship may qualify only when it identifies the exact KnowledgeItem ID and version through an application-validated immutable TaskKnowledgeReference, and the Task's Context manifest proves that the same version entered that Task's Context. The referenced version must have been eligible for the relevant Team when that Context was constructed. Eligibility is evaluated at that historical point: later retirement or replacement does not retroactively invalidate a reference that was valid at Context construction. A nonexistent item/version, cross-Team reference, wrong version, version that was ineligible at Context construction, or version absent from the Task's Context is an unsupported attribution attempt and can never qualify. Preserve the validation failure reason in the review evidence and unsupported-attempt reporting. Do not silently substitute a different or newer KnowledgeItem version.

Technical validation before substantive attribution review (RW-D62): every claimed relationship that fails the deterministic checks in RW-D61 remains visible as an attribution attempt and is classified non-qualifying, with its specific validation failure reason preserved. Do not send a technically invalid relationship through subjective material-influence review; it cannot qualify regardless of the explanation supplied. Only relationships that pass deterministic reference validation proceed to independent reviewer assessment of whether the retained knowledge materially influenced the claim under D50 and the qualifying/non-qualifying/indeterminate classifications in D53. Report technical validation failures separately from reviewer judgments that a technically valid reference was not materially influential. This makes technical integrity failure distinguishable from a valid reference that does not substantively support the claim.

Definition of a claim-level attribution attempt (RW-D63): an attribution attempt exists only when the output or its accompanying structured attribution data explicitly associates an identified claim with one or more specific KnowledgeItem references. A general statement that retained knowledge or memory was used does not establish claim-level attribution. A specific reference counts as an attempt even when it fails D61's deterministic validation and is therefore classified non-qualifying under D62. Reviewers must not invent missing KnowledgeItem references or infer use solely because relevant knowledge was available to the Task. If no explicit claim-level reference is present, the claim remains unattributed; it is not counted as a failed attribution attempt. This keeps attribution reporting grounded in recorded references rather than model assertions or reviewer reconstruction.

Claim-level roll-up across multiple attribution relationships (RW-D64): assign every identified claim exactly one mutually exclusive reporting category. A claim with at least one qualifying relationship belongs to the qualifying category even when it also has invalid, non-qualifying, or indeterminate relationships. A claim with no qualifying relationship but at least one explicit attribution attempt belongs to the attempted-but-not-qualifying category. A claim with no explicit reference belongs to the unattributed category. Preserve relationship-level reporting for every claimed reference: the claim-level category must not hide additional failed or indeterminate relationships attached to that claim. Technical validation failures remain included in the non-qualifying relationship total and must also be reported separately. This allows claim-level coverage to remain mutually exclusive without discarding relationship-level integrity information.

Claim-use coverage reporting (RW-D65): for each of the 10 treatment outputs, report both raw counts and percentages for the three mutually exclusive claim categories defined in D64: claims with at least one qualifying relationship; claims with explicit attribution attempts but no qualifying relationship; and claims with no attribution attempt. Also report aggregate counts and percentages across all treatment claims. Show the per-output distribution alongside the pooled treatment result; a pooled percentage alone could conceal inconsistent use across outputs. Calculate percentages using each output's reconciled claim inventory as its denominator, and use the combined reconciled claim inventory for the aggregate denominator. Do not add a new percentage acceptance threshold. The predeclared D51 gate remains at least one independently verified qualifying claim across the treatment condition; the full distribution supports interpretation of consistency without changing that gate.

Interpretation boundary for claim-use coverage (RW-D66): D65 percentages describe how recorded attribution is distributed across the complete identified-claim inventory. They do not measure the proportion of claims for which retained knowledge was relevant or applicable. An unattributed claim is not, by itself, evidence of a missed opportunity or model failure. Keep substantive knowledge relevance separate from recorded attribution coverage; do not infer relevance, applicability, or missed use merely from the presence or absence of a claim-level reference. Any separate assessment of whether retained knowledge was relevant to a claim requires its own explicit method and independent support, authorized through a later decision. This interpretation boundary does not modify the D51 acceptance gate.

Per-output relationship-level reporting (RW-D67): for each of the 10 treatment outputs, report counts of qualifying, non-qualifying, and indeterminate claim-to-knowledge relationships. Within the non-qualifying total, separately count relationships rejected by deterministic technical validation, preserving their specific validation failure reasons. Also report aggregate relationship counts across all treatment outputs. Retain both reviewers' original classifications, the disagreements between them, and the final adjudicated classification wherever adjudication occurs; aggregate counts must not replace the underlying review records. Do not introduce a new percentage or count acceptance threshold. This relationship-level view complements D65's per-output and aggregate claim-level distribution and makes repeated technical failures or concentration of qualifying relationships visible.

Duplicate claim-to-knowledge relationships (RW-D68): within one output, treat a relationship as uniquely identified by the reconciled claim ID and the exact KnowledgeItem ID and version. Repeated mentions of that same claim-to-version association count as one relationship, even when the reference appears multiple times in the output or accompanying attribution data. The same KnowledgeItem version linked to different claims produces separate relationships, and different KnowledgeItem IDs or versions linked to one claim also produce separate relationships. Preserve repeated occurrences in the immutable output or underlying attribution/review evidence where useful for audit, but do not inflate unique relationship counts or silently collapse distinct versions. Retain the originating LearningChange identity as provenance under D49.

Unique relationship review unit (RW-D69): independently assess each unique claim-to-knowledge relationship defined by D68 once per reviewer. Repeated occurrences of the same relationship are available as supporting review evidence, but they do not create additional relationships or require repeated classifications. Reviewers may consider all recorded occurrences when deciding whether the retained knowledge materially influenced the claim. Preserve occurrence-level references where useful for audit alongside the single relationship-level assessment. Apply D54's two-reviewer agreement and disagreement/adjudication process to the unique relationship.

Relationship identity across outputs (RW-D70): identify a unique claim-to-knowledge relationship by the combination of output ID, reconciled claim ID, exact KnowledgeItem ID, and KnowledgeItem version. Claim IDs are scoped to their output; the same claim-to-knowledge reference appearing in different outputs therefore represents separate relationships and must not be globally deduplicated. Deduplicate repeated occurrences only within the same output. Preserve each output's relationship and review records independently, then aggregate those records for treatment-level reporting. Retain the originating LearningChange identity as provenance under D49.

Relationship counts and claim-level denominators (RW-D71): report unique claim-to-knowledge relationships using D70's output-scoped identity, and report D64's mutually exclusive claim categories as a separate measure. Do not express relationship counts as percentages of claims: a claim can have more than one unique relationship, so claim counts are not a valid denominator for relationship percentages. Report qualifying, non-qualifying, and indeterminate relationships, including separately identified technical validation failures, as raw counts. Retain D65's claim-level counts and percentages without changing their denominators. Connect both reporting levels through output IDs and reconciled claim IDs so treatment aggregates can be traced back to individual outputs, claims, and review evidence.

Control-output attribution and isolation (RW-D72): retain any explicit claim-to-KnowledgeItem references in control outputs as attribution attempts and subject them to the same deterministic checks defined in D61–D62. A reference to a KnowledgeItem version absent from that control Task's Context cannot qualify, because availability to the Task is a prerequisite for claim-level use attribution. Report control attempts, validation failures, and any subsequent substantive classifications separately from treatment relationship counts; they do not enter the treatment claim-use acceptance gate. Control Tasks must not receive the frozen treatment experience snapshot under D27 and D29. If a control Task's Context manifest shows that experience from that snapshot was included, record and investigate it as a potential run-isolation breach under D29, not merely as a non-qualifying attribution attempt.

Disposition of a confirmed run-isolation breach (RW-D73): when investigation confirms that a control Task received experience from the frozen treatment snapshot, preserve the original run and its Context manifest, output, and attribution records as immutable evidence, and mark the run protocol-compromised. Do not silently delete or replace it. Record the evidence and reason for any decision to exclude it from the primary comparison, while keeping it visible in the complete run report. Report a sensitivity view that shows how the compromised run affects the comparison. A replacement run is permitted only under a procedure declared before replacement and applied consistently; it must not be an ad hoc response to the observed content or score. This keeps protocol deviations visible and prevents post-hoc repair of inconvenient results.

Treatment snapshot access and isolation (RW-D74): verify for every treatment run that the exact frozen experience snapshot specified by D29 was available through the intended retrieval path. The requirement is correct snapshot access, not successful retrieval of every item in that snapshot. A missing, incomplete, or incorrect snapshot configuration is a potential protocol violation. Preserve the original run, Context manifest, output, and related evidence; do not silently repair the Context or rerun the output. Investigate and classify the deviation using the transparency requirements established in D73: retain the run in full reporting, document the evidence and rationale for any exclusion from the primary comparison, and provide a sensitivity analysis showing its effect. Any replacement must follow a predeclared procedure applied consistently rather than being selected in response to observed output or score.

Frozen treatment snapshot identity and consistency (RW-D75): identify the treatment experience snapshot using an immutable snapshot ID or equivalent durable identity, and compute or retain a cryptographic hash over its canonical contents or manifest. Record both identity and hash in each treatment run's execution evidence. Verify across all 10 treatment runs that the same frozen snapshot identity and hash were made available through the intended retrieval path. Missing or unverifiable identity/hash evidence, or any mismatch, is a potential protocol violation subject to D74's preservation, investigation, and reporting rules. This proof establishes that the intended snapshot was consistently identified; it does not prove that particular items were relevant, retrieved, or materially used in an output claim.

Frozen snapshot manifest contents (RW-D76): the canonical manifest must enumerate every included KnowledgeItem ID and exact version, and record the originating LearningChange ID associated with each included version. It must also identify the Team, record the snapshot freeze time, and preserve the eligibility state used when the snapshot was constructed. The cryptographic hash required by D75 is computed over this canonical manifest rather than an arbitrary serialization. Mutable presentation details and retrieval ranking are excluded from snapshot identity unless they are explicitly designated as part of the frozen experience data. The manifest defines which experiences were members of the frozen snapshot; it does not claim that every member was retrieved for, or entered the Context of, every individual Task.

Canonical frozen-manifest serialization (RW-D77): serialize the D76 manifest as deterministic canonical JSON under a documented schema and explicit serialization rules. Sort KnowledgeItem entries by stable identity, using KnowledgeItem ID and then version. Use explicit field names and stable representations for timestamps and eligibility state. Formatting, insignificant whitespace, and object-key ordering differences must not produce different hashes for the same canonical manifest. Include a manifest-schema version so a future format change cannot silently reinterpret an earlier snapshot. Preserve the exact canonical manifest bytes together with the cryptographic hash, allowing the frozen snapshot identity to be independently reproduced and checked.

Frozen snapshot hash contract (RW-D78): compute SHA-256 over the exact canonical manifest bytes preserved under D77. Store or report the algorithm identifier explicitly as `sha256` alongside the digest, and encode the digest as lowercase hexadecimal. The algorithm is part of the snapshot's verification contract and must not be silently changed for an existing snapshot. A future algorithm change requires an explicit versioned decision and must retain the original algorithm, digest, canonical bytes, and a means to verify the original snapshot identity.

Frozen snapshot hash verification procedure (RW-D79): compute and preserve the SHA-256 digest when the canonical manifest is frozen. Before the first treatment run, independently recompute the digest from the preserved canonical manifest bytes and verify that it matches the frozen identity. For each treatment run, verify that the snapshot made available through the intended retrieval path corresponds to that same immutable identity and digest, and preserve the verification result in the run's execution evidence. Missing verification evidence or any mismatch is a potential protocol violation subject to D74's preservation, investigation, and reporting requirements; do not silently repair the Context or snapshot. A successful hash check proves snapshot identity and consistency only. It does not establish retrieval relevance, retrieval quality, or actual claim-level use.

Snapshot immutability and post-freeze changes (RW-D80): once frozen, the snapshot's manifest, canonical bytes, SHA-256 hash, and membership are immutable. Any addition, removal, replacement, or change to a KnowledgeItem creates a new snapshot identity and hash; the existing snapshot must never be overwritten. Before the first scored run, a corrected snapshot may be frozen, but the complete pre-run identity and hash verification required by D79 must be repeated. After the first scored run, remaining runs must not silently switch to a different snapshot. A necessary change requires stopping the affected experiment and obtaining an explicit Operator decision on whether to restart with a newly frozen snapshot. Preserve the original snapshot and all runs already performed as historical evidence, including any runs that cannot be part of a restarted primary comparison.

Restarted experiment instance (RW-D81): a restart following a post-start snapshot change is a new experiment, identified by a new experiment ID and a new frozen snapshot identity. Complete a fresh controlled comparison with all 10 control and 10 treatment runs; do not combine runs from the stopped instance with new runs to satisfy either condition's run count. Preserve the previous instance and all of its results as historical evidence, explicitly marked stopped or superseded. Reuse the same frozen brief, source corpus, answer key, rubric, and acceptance thresholds unless a separate Operator decision explicitly authorizes a change. Apply the isolation, randomization, snapshot identity, and verification requirements anew to the restarted instance. Report each experiment instance separately and never pool their scores into one primary comparison.

Run slots, execution attempts, and retry policy (RW-D82): assign a stable run-slot ID to each of the 20 planned runs and a distinct attempt ID to every execution attempt within a slot. Preserve each failed or interrupted attempt, including its inputs, configuration, logs, and recorded failure reason. Retries are permitted only for technical failures defined in advance and occurring before a scored output has been produced. An output must never be retried because it is poor, unexpected, or receives an unfavorable score. Apply the same predefined retry rules to control and treatment. Record every retry and exclusion transparently; only valid completed runs count toward the 10 completed runs required for each condition. Do not silently replace a completed run or discard an earlier attempt.

Retry-eligible technical failure boundary (RW-D83): a retry is eligible only when there is objective evidence of a predefined technical failure and no complete output artifact was produced by that attempt. Eligible examples are temporary provider unavailability or server errors, transient network failure or request timeout, temporary rate limiting, and worker or execution-process interruption before output completion. Preserve any partial output as part of the failed attempt. Invalid input, configuration, or experiment setup and prompt or contract violations are not retry-eligible. Neither is an attempt that produced a complete output, even if that output is malformed, refuses the task, or performs poorly. A failure discovered only after examining output quality or score cannot justify a retry. Preserve every attempt, its evidence, and its failure classification; apply this boundary identically to control and treatment.

Maximum retry budget (RW-D84): permit one retry after the initial attempt, for a maximum of two attempts per run slot. Apply the same limit to control and treatment. The retry must independently meet D83's objective technical-failure and pre-completion criteria. When the permitted attempt is exhausted, mark the original slot technically incomplete and preserve all evidence. A technically incomplete slot does not count toward the 10 valid outputs for its condition. Any replacement is separately governed by D85 and the reconciled rule in D130.

Replacement run-slot limit (RW-D85): permit one replacement for an original slot that remains technically incomplete after its initial attempt and one D84 retry. The replacement stays in the same condition, uses the same frozen inputs/configuration/snapshot, has a new run-slot ID linked to the original, and receives the D83 eligibility criteria and D84 one-retry limit. Require explicit Operator disposition under the predeclared replacement procedure. Never replace a valid output for content or score; no further replacement is allowed if the replacement is also technically incomplete. If the condition remains below 10 valid outputs, report the experiment as incomplete.

Run-slot randomization and replacement scheduling (RW-D86): define all 20 original run slots before execution, assigning 10 to control and 10 to treatment. Randomize their execution order through a documented procedure and preserve the randomization seed and resulting order. Do not create a replacement slot until its original slot has been formally classified as technically incomplete under D82–D85. A replacement remains in the same condition and receives an execution position through a scheduling rule declared before replacements are needed; its position must not be selected in response to earlier outputs, their content, or their scores. Preserve the identities of original and replacement slots, their relationship, actual execution order, and complete attempt history. Include replacements in full reporting while distinguishing them from the original 20 planned slots.

Randomization reproducibility record (RW-D87): preserve the randomization algorithm and its version, the exact initial list of 20 run-slot IDs and their condition assignments, the seed, and the complete execution order generated from those inputs. Freeze this record before the first scored run so an independent reviewer can reconstruct the original order. Do not regenerate or modify the order in response to observed output or scores. Use the same documented and reproducible method for replacement scheduling, while retaining replacement slots as separately identified records linked to their original exhausted slots.

Blocked run-order randomization (RW-D88): divide the 20 original run slots into five blocks of four. Assign exactly two control slots and two treatment slots to each block. Randomize both the order of the five blocks and the order of the four slots within each block, preserving the resulting assignments and sequence in the D87 reproducibility record. This balances the conditions across the execution timeline while retaining randomized order within blocks. Schedule any replacement slots separately under the predeclared replacement procedure; do not alter or regenerate the original 20-slot randomized sequence when a replacement becomes necessary.

Run timing and operational windows (RW-D89): execute each block of four runs within one predefined operational window, retaining the frozen interleaved order of its two control and two treatment slots. Keep the provider, model version, generation settings, and infrastructure configuration constant throughout the experiment. Record start/end timestamps and relevant provider or infrastructure incidents for every execution attempt. Do not selectively pause, accelerate, or reorder one condition in response to observed output content or quality. If a material provider or infrastructure change is necessary, pause the experiment and assess whether the frozen execution protocol and comparability remain valid before any resumption. Preserve the original randomized sequence; an operational interruption does not authorize rerandomization.

Material execution changes and operational events (RW-D90): pause the experiment and complete an explicit protocol-validity assessment before resuming after any material change. Material changes include provider or model replacement; model-version or model-weight changes; generation-parameter changes such as temperature, sampling, or token limits; changes to system prompts, task prompts, or Context construction; changes to retrieval configuration or embedding models; and infrastructure changes that may alter model inputs, outputs, timing behavior, or reliability. A material change does not automatically invalidate the experiment, but its effect on the frozen protocol and comparability must be assessed before work resumes. Record routine monitoring and logging, maintenance that does not alter the execution environment, and temporary incidents handled under the existing retry policy without changing frozen configuration. These routine events do not, by themselves, trigger a pause under this decision.

Resumption authority after a material execution change (RW-D91): before any resumption, preserve the configuration before and after the change, including exact versions and relevant timestamps. Identify the run slots and conditions that may have been affected, assess whether experimental inputs, outputs, or comparability changed, and document the supporting evidence, uncertainties, and affected runs. Resumption requires explicit Operator authorization. An agent or model may prepare the evidence and recommendation but cannot authorize its own resumption. The Operator must explicitly choose one of three outcomes: resume with the protocol deviation documented; stop the experiment; or restart as a new experiment instance under D81. Do not resume merely because a technical issue appears resolved.

Criteria for resuming the same experiment (RW-D92): resume within the existing experiment instance only when the documented assessment concludes, on protocol and execution evidence rather than observed output quality or scores, that the original control/treatment comparison remains scientifically defensible. The assessment must identify completed and pending run slots that may be affected and explain the basis for the comparability conclusion. If comparability cannot be established, stop the experiment or restart it as a new instance under D81. A resumed experiment retains its original randomized run order and complete configuration history; do not erase or rewrite the deviation. Disclose the deviation in final reporting. Include a sensitivity analysis whenever the deviation could plausibly affect the results. Neither favorable nor unfavorable observed scores or outputs may be used as the basis for declaring the protocol valid or invalid.

Independent review and authority for execution incidents (RW-D93): the implementation agent or Operator prepares an incident record containing the change, before/after configuration and exact versions, affected run slots and conditions, timestamps, and supporting technical evidence. A reviewer who did not make the change independently examines whether the frozen protocol and control/treatment comparison remain scientifically comparable. The reviewer may recommend resumption, stopping, or restarting, but does not authorize resumption. The Operator makes the final explicit decision and records its rationale under D91–D92. Where practical, the independent review is performed without exposing output scores or condition-level performance, so the validity judgment is not influenced by observed results. Preserve the reviewer's assessment and the Operator's decision alongside the incident evidence.

Independent reviewer qualification and conflicts (RW-D94): the reviewer must not have made the material change or executed the affected runs, and must not have a direct incentive tied to obtaining a passing result or completing the experiment by a particular date. The reviewer must understand the frozen experiment protocol and be competent to evaluate the technical evidence relevant to the incident. The review is limited to protocol validity and comparability; it does not rescore outputs or reinterpret acceptance thresholds. Disclose any potential conflict of interest. If independence cannot reasonably be established, preserve that limitation explicitly and do not characterize the review as independent. The reviewer may provide a recommendation, but the Operator retains final authority under D91 and D93.

Incident review record (RW-D95): retain a structured record for every material execution incident. It must identify the incident and affected experiment/run slots; describe the reported change and preserve exact before/after configurations, versions, and timestamps; identify the evidence reviewed and include the reviewer's independence and conflict-of-interest declaration; assess affected inputs, outputs, and control/treatment comparability; and state explicit uncertainties and limitations. The independent reviewer records a recommendation to resume, stop, or restart. The Operator's final decision and rationale are recorded separately and must not overwrite or be merged into the reviewer's recommendation. Preserve the original incident evidence, independent assessment, and Operator decision immutably, linked through the incident ID and affected experiment/run-slot IDs. Any subsequent decision is a new linked record, not an edit that erases the historical assessment or authorization.

Incident validity assessment outcomes (RW-D96): the independent reviewer's finding must use one of three classifications. **No material impact:** evidence shows that the change did not affect the frozen protocol or the control/treatment comparison. **Impact, but comparison remains defensible:** execution was affected, but evidence supports the conclusion that the original comparison remains scientifically defensible, subject to a documented protocol deviation and any necessary sensitivity analysis. **Comparability not established:** evidence is insufficient, or indicates that the original comparison cannot be established as defensible. This third finding is not equivalent to proof that the experiment is invalid; it means validity has not been established. The reviewer records the classification and supporting evidence in the incident review. The Operator retains final authority under D91–D93 and makes the explicit decision to resume, stop, or restart.

Experiment protocol-deviation register (RW-D97): maintain a complete register of every deviation from the frozen experiment protocol. Assign each deviation a unique ID and link it to its incident record, affected experiment and run-slot IDs, and the corresponding validity assessment. Record when it began and ended, its duration and scope, its classification, and its resolution. Distinguish deviations assessed as having no material impact from deviations that may affect comparability. Disclose every deviation in the final report, including those assessed as non-material and those for which the Operator authorized resumption. An authorization to continue changes the permitted execution path; it does not erase the deviation, its evidence, or its historical record.

Protocol-deviation severity classification (RW-D98): classify each deviation as **minor**, **material but contained**, or **critical**. A minor deviation has no reasonably expected effect on experimental inputs, outputs, or comparability. A material-but-contained deviation involves an effect that occurred or is plausible, but the documented assessment establishes that the original comparison remains defensible. A critical deviation prevents the original comparison from being established as scientifically defensible. The independent reviewer proposes the classification based on the evidence; the Operator confirms the final disposition. A critical deviation requires stopping the experiment or restarting it as a new instance; it cannot be resolved by simply authorizing continuation. Where evidence is insufficient to support a definite classification, preserve that uncertainty rather than forcing a lower-severity label.

Minimum R7-C capability for the first newsroom scenario (RW-D99): include only the application-written immutable TaskKnowledgeReference and the minimal typed, application-validated KnowledgeUseAssessment required for auditable claim-level attribution. The reference connects an identified output claim to the exact KnowledgeItem ID and version, originating LearningChange, relevant Team eligibility, and immutable Task Context evidence. The assessment links that evidence to the later Task's terminal Outcome. These records do not establish causation, grant knowledge-mutation or approval authority, or create a broader autonomous evaluation/learning loop. Retrieval benchmarks, label provenance, blinded human claim-use review, adjudication, statistical reporting, and score aggregation remain responsibilities of the newsroom harness rather than production Watch subsystems. This decision freezes the minimum capability requirement; it does not independently authorize the R7-C milestone or implementation.

Persistent Artifacts and publishing scope (RW-D100): exclude persistent production Artifacts, general-purpose rendering, publishing, distribution, and delivery workflows from the first newsroom scenario and RW foundation. Preserve source packets and manifests, model outputs, Context manifests, execution records, and reviewer assessments as experiment-harness evidence; preserving those records does not require or imply a production Artifact subsystem. This exclusion does not revoke the accepted ADR-0007/ADR-0020 EvidenceLink target vocabulary, including Artifact as a source. Artifact support may remain staged until an Artifact entity and an explicitly authorized use case exist. Reconsider persistent deliverables only if the frozen newsroom scenario demonstrates a concrete requirement and the Operator explicitly authorizes the scope change.

Story eligibility (RW-D101): select one completed science-and-technology story for the scored experiment. It must have accessible primary evidence, directly verifiable important claims, meaningful interpretive depth, bounded scope, and sources that can be preserved and independently checked. Exclude breaking or rapidly changing stories; stories primarily dependent on anonymous or inaccessible sources; stories whose evidence cannot distinguish established findings from speculation; and stories whose necessary specialist knowledge cannot be represented in the packet. The decision freezes eligibility criteria, not the identity of the selected story.

Source corpus composition and inclusion/exclusion (RW-D102): determine corpus size by evidentiary sufficiency. Prefer original research, official datasets, and direct institutional evidence. Add independent expert/institutional sources or reputable secondary reporting only when they contribute necessary context, verification, qualification, limitations, or relevant alternative interpretations. Every included source must contribute direct evidence or necessary context. Exclude duplicative sources that add no evidence, irrelevant sources, unverifiable or inaccessible sources, and primarily promotional material. Disagreement with a preferred interpretation is not by itself grounds for exclusion. Record important excluded candidates and reasons.

Corpus freeze and versioning (RW-D103): freeze the reviewed corpus before drafting the final scored assignment brief. Give it a unique ID and version; preserve a manifest with stable source IDs, metadata, retrieval dates, and cryptographic hashes; and retain exact source files or stable archived copies where possible. Do not add or silently replace sources after freeze. Document corrections explicitly. A material corpus change requires a new version and an assessment of its effect on experimental validity, including whether a new experiment instance is necessary.

Scored newsroom assignment and condition parity (RW-D104): give every control and treatment output the same assignment, frozen packet, intended audience, scope, evidence rule, required elements, output format, and word limit. The audience is educated general readers without assumed specialist knowledge. Require use of the supplied packet and distinction between source-supported findings, interpretation, and uncertainty. Do not expose the answer key, preferred conclusions, or detailed scoring rubric to generation. This refines the assignment audience and restates condition parity without changing the accepted 10-control/10-treatment design or evaluation method.
Claim-verification and editorial point allocations (RW-D112): allocate the claim-verification component's 50 points to factual accuracy (20), evidence traceability (15), quotation and attribution accuracy (7), and numerical and temporal accuracy (8). Allocate the editorial component's 50 points to interpretation (12), significance (10), uncertainty and limitations (15), and synthesis (13).

Anchored category scoring (RW-D113): use five levels for every category: 4 complete, 3 strong, 2 partial, 1 weak, and 0 absent/incorrect. Category points equal the category maximum multiplied by the level and divided by four. Story-specific examples and detailed instructions are frozen with the source-grounded answer key and rubric before scored runs. Do not reward verbosity, preferred wording, or preferred conclusions.

Critical-error comparison (RW-D114): the treatment condition must not exceed control in either total distinct critical factual errors or the number of outputs affected by at least one critical factual error. Disclose and examine every critical error in both conditions; the aggregate score cannot conceal them.

Valid output count for the mean-score gate (RW-D115): calculate each condition's mean from 10 valid completed scored outputs. The first experiment requires 10 valid control outputs and 10 valid treatment outputs. Freeze validity, retry, and exclusion rules before execution; do not silently replace, omit, or reclassify runs after observing scores.

Matched execution pairs (RW-D117): organize the 10 control and 10 treatment runs into 10 matched pairs. Each pair uses the same frozen assignment, source corpus, model/provider configuration, generation settings, tool budget, and baseline identity. Treatment alone receives the frozen retained-experience snapshot through normal retrieval and Context. Report the condition-level comparison as primary and also report within-pair differences. Pairing is a blocking and reporting structure, not statistical proof or causal identification.

Randomized generation order (RW-D118): randomize the order of the 10 pairs before execution and independently randomize condition order within each pair. Preserve planned randomization, pair identities, planned order, and actual execution order/timestamps. This is distinct from reviewer presentation randomization under RW-D33.

Frozen execution configuration (RW-D119): identify and freeze the experiment configuration before scored execution: experiment ID/version; corpus and assignment identities; baseline and treatment-snapshot identities; provider/model and available revision/weight identity; generation parameters; system/task prompt versions or hashes; tool availability/budget; and retrieval/Context configuration. Record unsupported or unavailable fields as unavailable. Matching configuration records alone do not prove deterministic reproduction.

Immutable run-attempt evidence (RW-D120): preserve every attempt with experiment, pair, run-slot, condition, and attempt identities; planned/actual order; baseline and snapshot identities; corpus and assignment identities; model/provider configuration; prompt and Context references; Task and terminal Outcome references; exact output and cryptographic hash; timestamps, cost, latency, tool-call counts, status, errors, and retries. Keep failed attempts even when a retry becomes the scored attempt.

Technical retry and replacement boundary (RW-D121): retain and evaluate any returned response, including poor, incomplete, malformed, or refused responses; response quality is not a retry reason. Allow one retry only for an objectively evidenced D83 technical failure before a complete output exists, preserving the same slot, condition, inputs, configuration, and snapshot. Preserve every attempt, failure, timestamp, and cost. If that retry also fails, the original slot is technically incomplete; it may receive one separately identified replacement only under D85/D130 and explicit Operator disposition, never because of output quality or score.

Official output scores (RW-D123): use each output's final reconciled or adjudicated score in the condition-level and matched-pair comparisons. Preserve both initial reviewer scores, critical-error judgments, disagreements, adjudication rationale, and final score. Do not substitute an average for the preserved reviewer evidence.

Score summaries and matched-pair reporting (RW-D124): report, for each condition, mean, median, minimum, maximum, category-level results, and every individual score. Report all 10 matched-pair differences. The condition-level mean difference remains the primary quality acceptance comparison under RW-D28; other summaries are descriptive and add no acceptance threshold.

Uncertainty and interpretation limits (RW-D125): report observed distributions, spread, paired differences, incomplete slots, and relevant uncertainty/limitations. Do not add a p-value, significance test, confidence-interval threshold, or inferential-statistics requirement as an acceptance gate. Ten runs per condition constitute a bounded engineering evaluation, not evidence of general statistical superiority or broad causal effectiveness.

Separate result dimensions (RW-D126): report newsroom quality, critical factual errors, claim-level retained-knowledge attribution, independent outcomes/confidence bands, deterministic validation acceptance/rejection, and operational measures separately. Retrieval/Context availability is not claim-level use; claim-level use is not proof of output improvement; and improved scores alone do not establish that retained knowledge caused the improvement.

Acceptance-gate status (RW-D127): label each of the three predeclared gates pass, fail, or not assessable. Pass requires available evidence meeting the predeclared condition; fail means evidence shows it was not met; not assessable means evidence is missing, incomplete, or insufficient. A not-assessable primary gate cannot be presented as a successful harness pass. The Operator retains final acceptance authority.

Final report structure (RW-D128): include experiment identity and frozen protocol; corpus, assignment, baseline, and snapshot identities; planned runs, attempts, retries, and incomplete slots; reviewer process/adjudication; total, category, individual, and paired scores; critical errors; claim-level use; independent outcomes/confidence bands; cost, latency, failures, and the full deviation register; limitations and interpretation; and each primary gate's disposition and the Operator's decision. Disclose all runs and deviations, including compromised/excluded runs and the evidence/rationale for any exclusion from the primary comparison.
Matched execution blocks and pairs (RW-D129): preserve 10 matched pairs while assigning two complete pairs (four run slots: two control and two treatment) to each of five blocks. Randomize block order, pair order within each block, and condition order within each pair. Execute each block within its predefined operational window. Preserve the reproducibility metadata required by D86–D89 and D117–D118; pairing and blocking are complementary, not competing, structures.

Consolidated retry and replacement policy (RW-D130): there is one retry after the initial attempt per slot under D84. An exhausted technically incomplete original slot may receive at most one separately identified replacement under D85, with explicit Operator disposition and predeclared scheduling under D86–D87. The replacement uses the same frozen condition inputs/configuration, receives the same one-retry limit, and inherits the original slot's matched-pair and block IDs for analysis while retaining a new slot ID and separate execution position. No valid output may be replaced, no replacement may depend on output quality or score, and a replacement cannot itself be replaced. D130 reconciles D84–D85 with D121–D122.

Shared EvidenceLink architecture (RW-D131): preserve one shared EvidenceLink model/table with subjects `hypothesis` and `evaluation` and sources `signal`, `outcome`, `artifact`, and `consultation`. Retain immutable hashed Snapshot and exact quote/offset validation, same-Team ownership, existing Evaluation evidence, and stance values `supports`, `challenges`, and `mentions`; only the first two may cause ConfidenceChanges. Artifact operation may remain staged until an entity/use case is authorized. Operational Consultation entities/Tasks remain deferred under D12; the accepted Consultation source vocabulary remains in the target contract.

EvidenceLink physical design gate (RW-D132): RW-0 freezes the conceptual contract, not the schema representation. RW-1 must produce the exact relational model, keys/FKs, constraints, indexes, compatibility/backfill, migration, staged-source, downgrade, and preservation design, and obtain explicit Operator acceptance before implementing related schema, migration, or code changes.

Minimum R7-C slice mapping (RW-D133): only D99's immutable TaskKnowledgeReference and minimal typed KnowledgeUseAssessment are included. The implementation plan must assign each capability to a named RW slice and its proofs before that slice is authorized. This does not authorize R7-C as a separate milestone or any broader benchmark or autonomous learning/evaluation subsystem.

Mandatory proof and delivery controls (RW-D134): apply the existing proof matrix and per-slice delivery rules throughout RW-1–RW-5. Each bounded slice records exact test nodes or approved non-automated evidence for applicable proofs, regression tests, required mutation/race evidence, disposable-PostgreSQL results, separate exact implementation and PR-head SHAs, and corresponding local/hosted evidence. Ordinary CI uses deterministic stub providers; live provider smoke testing remains separate. No new generic process framework, complexity-budget system, or speculative test infrastructure is added.

Decision freeze, documentation closeout, and authorization (RW-D135): approval of Groups 1–8 completes the decision freeze but not the RW-0 milestone or implementation authorization. Documentation closeout requires reconciled authoritative documents and either a frozen newsroom scenario package or an explicitly tracked pre-execution package deliverable with a named owner and acceptance gate. The actual story, corpus/manifest, scored brief, answer key, independent outcome reference, story-specific scoring examples, and execution configuration must be frozen before scored runs. PLAN.md remains the sole authority for milestone status. RW-1 and every later slice require separate explicit Operator authorization.
No quality-based early stopping and incomplete runs (RW-D122): do not stop early based on observed quality or scores. Fewer than 10 valid completed outputs in either condition cannot pass the mean-score gate. An original slot technically incomplete after its permitted retry may receive only the one predeclared technical replacement under D85/D130 and explicit Operator disposition; preserve both slots and all attempts. No replacement may be chosen or scheduled in response to any output quality or score. If the allowed process cannot produce 10 valid outputs per condition, report the experiment as incomplete. Material changes, incidents, resumption, deviations, and restarts remain governed by D90–D98 and D81.
Descriptive measures (RW-D116): report deterministic validation acceptance/rejection and confidence-band calibration, including denominators, counts, and limitations, but do not impose additional pass/fail thresholds on these measures. The three primary acceptance gates remain those in RW-D28; no fourth gate is added.
Reviewer independence and declarations (RW-D110): reviewers must not have generated any scored output. Where practicable, they should also be independent of story/source selection and answer-key preparation. Preserve each reviewer's identity, relevant qualifications, conflict-of-interest declaration, relationship to the experiment, and any limitation that may affect assessment.

Material scoring disagreement and adjudication (RW-D111): preserve both independent assessments and first attempt resolution against the frozen answer key and rubric. Where a material scoring disagreement remains unresolved, a third qualified reviewer adjudicates it. Do not automatically average conflicting scores or conceal the disagreement. Preserve original judgments, adjudication rationale, and final score separately.
Independent outcome reference set (RW-D105): prepare a separate, versioned reference set before scored execution. For each material tracked finding or Hypothesis, preserve a stable ID, statement and scope, supporting and challenging evidence with exact source references, resolution conditions, status, and rationale. The set must be independently checkable against frozen evidence and must not derive conclusions from scored model outputs.

Outcome classifications (RW-D106): classify each finding as supported, contradicted, or unresolved. Support or contradiction requires the predefined resolution conditions to be met. Insufficient or conflicting evidence remains unresolved. Absence of evidence is not contradiction, and unresolved findings must not be forced into a binary result.

Resolution criteria and evidence cutoff (RW-D107): define resolution criteria before observing scored outputs and freeze them with the outcome set. Establish a fixed evidence cutoff. Later discoveries do not silently alter the original result; preserve them as subsequent evidence and assess whether a new reference-set version or experiment is necessary. Retain conflicting evidence and the rationale for each resolution.

Confidence calibration (RW-D108): use the existing Low, Moderate, and High ordinal bands. For each band, report resolved and unresolved sample counts and the observed resolution rate among resolved cases. Unresolved cases are neither correct nor incorrect. Do not invent numerical probabilities or calculate a Brier score without an independently justified and explicitly approved mapping. Interpret small samples cautiously.

Outcome independence and post-freeze changes (RW-D109): determine the reference outcomes independently of scored model outputs. Preserve source references, versions, original classifications, evidence, and change history. Blind human outcome reviewers to condition where feasible. Model evaluations may contribute evidence but cannot be the sole authority. Document, version, and assess any post-freeze change for experimental validity.
Claim-level retained-knowledge use (RW-D49): count use only when a specific output claim is linked to the exact accepted KnowledgeItem version and originating LearningChange; an immutable TaskKnowledgeReference and Context manifest establish that the same version entered that Task's Context; application validation confirms identity, version, eligibility, and Context linkage; and independent reviewers judge whether the knowledge materially supports, qualifies, or informs the claim. Retrieval or Context availability alone is availability, not use, and an unsupported model assertion of use is insufficient. This provides auditable claim-level use without claiming access to hidden reasoning or proving causation.

Source citation and claim attribution (RW-D48): require explicit packet-ID attribution for direct factual claims. For interpretations and implications, identify the packet evidence on which they rely and distinguish the analysis from source-reported findings. Explicitly acknowledge uncertainty and material points the packet does not establish; do not present unsupported claims as established facts. This enables claim-level review without imposing identical wording or a rigid citation style.

Scored output length and presentation (RW-D47): apply one common word limit to all 20 outputs, choosing its exact value after the story and brief are drafted. Require material to appear within the defined sections, identify sources consistently by packet IDs, and prohibit extra material outside the required sections. Do not require identical wording or conclusions, and do not reward verbosity; concise outputs receive full credit when they adequately cover the required elements.

Scored output structure (RW-D46): require a consistent structured editorial analysis with a headline, central finding, why it matters, evidence and source comparison, limitations and uncertainty, and what remains unknown. This supports comparable review without prescribing conclusions or wording. Set the exact common word limit when drafting the brief and apply it equally to all runs.

Scored assignment brief structure (RW-D45): use the same fixed structure for every run: task, intended audience, scope and exclusions, evidence rule, required analytical elements, and consistent output format and length limit. The evidence rule limits the model to the supplied source packet and requires it to distinguish source-supported findings from interpretation and uncertainty. Required elements include the central finding, significance, limitations, uncertainty, and comparison of relevant sources. The brief must not disclose the answer key, preferred conclusions, or specific expected claims. Control and treatment receive identical instructions.

Source packet and assignment freeze order (RW-D44): select a candidate story, collect and review candidate primary sources, then freeze the source packet and manifest. Write the scored newsroom assignment brief using only that frozen packet. Prepare the independent answer key, then freeze the brief, answer key, and rubric before scored runs. This order prevents the assignment brief from steering source selection toward a desired conclusion.

Newsroom story selection (RW-D43): choose a story with accessible primary research or equivalent evidence; important factual claims must be directly verifiable against the frozen source packet; the subject must offer meaningful significance, limitations, or uncertainty to analyze; scope must remain bounded; and sources must be preservable for reproducibility. Avoid breaking news and rapidly changing subjects so the experiment measures retained experience rather than changes in available information.

Source-packet size (RW-D42): determine the number of sources by evidentiary sufficiency rather than a predetermined numerical target. The packet must contain enough relevant primary evidence to establish the central finding and its material qualifications, limitations, and conflicting evidence where that evidence affects interpretation. Keep it bounded enough for reviewers to verify claims reliably. Do not add sources merely to make the packet appear comprehensive.

Source corpus selection and freeze (RW-D41): prefer primary sources such as original research papers, official datasets, and direct institutional publications wherever available. Every included source must contribute relevant evidence. Include sources needed to represent important qualifications, limitations, and conflicting findings rather than selecting only evidence for one narrative. Preserve exact source files or stable archived versions with retrieval dates and cryptographic hashes. After the corpus is frozen, neither control nor treatment runs may receive additional sources. Record important candidate sources that were excluded and the reasons for exclusion. Freeze the corpus and version manifest before scored runs.

The methodology and thresholds are frozen by RW-D22–D29 and RW-D101–D135. The actual completed story, source corpus/manifest, scored brief, answer key, independent outcome reference, story-specific scoring examples, reviewer calibration samples, and execution configuration are not selected/prepared here; they must be frozen before the first scored run or tracked as pre-execution deliverables with a named owner and acceptance gate.

The Operator has confirmed the target product claims (RW-D07), minimum KnowledgeUseAssessment boundary (RW-D08), harness/production boundary (RW-D09–D11), Consultation and human-input design boundaries (RW-D12–D13), human-configured Team and generalist defaults (RW-D14–D15), and the Thread-creation/update/commit behavior (RW-D16–D21). The first newsroom scenario and its measurement method are defined by RW-D22–D29 and RW-D101–D135: methodology, source/story eligibility, corpus freeze, assignment parity, reviewer protocol, outcome reference, 100-point rubric and gates, matched-pair/block execution, retries/replacements, reporting, and authority boundaries are approved. The concrete story package remains a pre-execution deliverable; decision approval does not imply that it has been prepared or scored. The minimum D99 R7-C capabilities remain separately gated and must be mapped to named RW slices under D133. The EvidenceLink architectural contract is frozen under D131; its physical database representation remains a separately accepted RW-1 design gate under D132. No RW implementation or scored execution is authorized by this record.

## 2. Accepted architecture constraints

These are existing accepted contracts, not new decisions made by this record.

### 2.1 EvidenceLink is one shared evidence model

- [ADR-0007](../decisions/architecture%20decision%20records%20%28ADR-0001%20-%20ADR-0019%29.md#adr-0007-generalized-evidence-links-with-deterministic-validation) defines polymorphic EvidenceLink subjects **hypothesis | evaluation** and sources **signal | outcome | artifact**. Quotes are validated deterministically against immutable hashed Snapshots; only **supports** and **challenges** can anchor ConfidenceChanges.
- [ADR-0020](../decisions/ADR-0020-consultations-waiting-happens-between-tasks.md) adds **consultation** as an EvidenceLink source. A Consultation answer is an immutable hashed Snapshot and can be cited using the same quote-validation rule.
- [ADR-0021](../decisions/ADR-0021-operator-update-path-human-as-first-class-worker.md) requires **operator_update** to use the same proposal and commit validation as **update_thread**. Human authorship is provenance, not a validation exemption.

RW must implement these accepted contracts through the existing EvidenceLink concept. A sibling evidence table or a human-only bypass is not the default design.

### 2.2 Current implementation is narrower than the accepted contract

At the code baseline audited for this checkpoint (**29c954fe8685e0a5ddb9b205277a28b1a158c57e**):

- **core/models.py** has an Evaluation-only EvidenceLink subject.
- Its supported source kinds are **signal** and **outcome**.
- It does not implement Hypothesis subjects, Artifact sources, or Consultation sources.
- **Thread**, **Hypothesis**, **ConfidenceChange**, and **SignalDisposition** are not ORM models in this baseline.
- The task names **triage_signal**, **update_thread**, **operator_update**, and **apply_decay** appear in specifications and an ingestion Event-scope allow-list; that allow-list is not an implementation of those Tasks.

This is an implementation gap against the accepted architecture, not a reason to replace the accepted model. The audit is pre-B6 and must be repeated read-only against the verified post-B6 main head before RW-1; no post-B6 re-audit is claimed by this record.

### 2.3 Evidence-model implementation rule

The implementation plan should extend the existing **evidence_links** contract to the accepted subject/source vocabulary while preserving current Evaluation evidence, quote/hash validation, same-Team ownership, uniqueness, and rejection semantics.

The exact relational representation, foreign-key strategy, and migration sequence remain RW-1 engineering work. If the accepted polymorphic contract cannot be implemented without changing an accepted decision, stop and submit an ADR addendum for Operator review before coding. Do not silently narrow ADR-0007 or create a parallel evidence system.

Artifact source support may be staged until an Artifact entity exists, but the accepted target vocabulary must remain explicit. Consultation support is not optional in the accepted target: ADR-0020 already includes it. The order in which those source types become operational must be stated in the RW-1 migration plan.
