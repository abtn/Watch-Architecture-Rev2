### G1 — True concurrent compare-and-set race on one KnowledgeItem
The revise regression constructs competing proposals and commits the winner before attempting the stale loser. The competing approval test likewise sequences the winner and loser. The inspected test inventory does not establish two concurrently executing PostgreSQL approval transactions racing on the same target.
**Required proof:** use separate sessions/transactions against disposable PostgreSQL with controlled synchronization. Exactly one canonical transition wins; the loser fails closed; no partial state, duplicate decision Event, duplicate version/pointer advance, or terminal success for the loser is persisted. Cover the shared compare-and-set boundary for revise and revalidate, or demonstrate why one parameterized common test proves both.

**G1 disposition (updated 2026-11-12):** G1 now contains two application-level approval serialization tests and two database CAS statement race tests. The application tests execute the real Operator adapter path with every production lock intact; the Team lock serializes the competing approvals. The stale loser is terminalized as a failed Task through TaskRuntime with one durable Outcome and terminal failure Events. TaskRuntime reconstructs the same stale failure on retry, while request replay verifies the immutable stored approval binding rather than recomputing against the now-stale target. The database tests synchronize two PostgreSQL transactions and execute `_knowledge_item_cas_statement`, the same statement builder used by `LearningCommitService`; the builder retains the production item/Team/pointer/version predicates and the revalidation `needs_review` predicate. This proves the database behavior of the production statement construction, not two full approval workflows simultaneously reaching CAS; the application tests separately prove the real locking path.

The production correction is limited to stale approval failure finalization/replay and extracting the existing CAS statement construction into a shared helper. No migration, schema, lock, or CAS predicate change was made. ### G2 — Revalidation approval crash/recovery after canonical decision commit
**Status: COMPLETE — PR #105 MERGED (2026-11-12).**

PR [#105](https://github.com/abtn/Watch-Architecture-Rev2/pull/105) adds the operation-specific regression `test_operator_commits_and_recovers_revalidation_after_finalize_crash` in `tests/test_experience_distiller.py`. It exercises the real trusted `OperatorApplicationAdapter` accepted-revalidation path. The test replaces `TaskRuntime.finalize` with a one-shot simulated process-loss exception at the commit/finalization boundary: the canonical revalidation decision commits, while the same approval Task remains recoverable and running.

Before recovery, the test verifies the accepted LearningChange is committed by the original approval Task; the KnowledgeItem remains active with its pointer, version, and content hash unchanged; exactly one request Event and one accepted-decision Event exist; no terminal Outcome exists yet; and the immutable request/assessment binding is retained. It then makes the original attempt eligible for interrupted recovery and calls the existing `TaskRuntime.recover_interrupted` path. Recovery completes the same Task without retrying the canonical decision. The test verifies the terminal Outcome/Snapshot/Event evidence, one `task_completed` Event, unchanged canonical KnowledgeItem state and decision payload, and preservation of the original Task identity and approval binding. A second recovery and replay of the captured terminal observation are idempotent: no duplicate Outcome, terminal Event, or decision Event is created.

The interruption is deterministic exception injection at the exact boundary, not an operating-system process kill. It directly exercises the durable post-commit/pre-finalization state and the existing recovery path. The test covers accepted revalidation only; it does not claim G5 rejected-approval replay or a separate rejected-revalidation crash-recovery proof.
