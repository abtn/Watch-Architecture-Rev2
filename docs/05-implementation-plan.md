# Implementation Plan for the Revised Architecture

## Guiding principle

Do not rewrite the entire project.

Do not implement the Control layer before the Kernel is working.

Make the smallest architectural change that proves the new Control model while preserving the existing reactive execution path.

## Slice K1 — Smallest Kernel commit path

Implement the `ingest_source` Kernel slice that proves:

```text
fetched content
    ↓
transient ingestion proposal
    ↓
deterministic validation
    ↓
content-addressed immutable Snapshot
    ↓
atomic database commit: Signal + Event
```

There are no model calls. K1 receives already-fetched content; it does not
implement a connector, scheduler, Trigger, API/CLI Task creation, queue, or
Task runtime.

### K1 preconditions and proposal

The implementation accepts one typed, transient ingestion proposal containing
the Task reference, configured source identity (`origin_url` and
`source_type`), fetch time, fetched bytes, and their claimed content hash.
Application code computes SHA-256 from the exact bytes and validates the claim.
The proposal is not persisted; K1 adds no Proposal entity/table or generalized
proposal framework. A standard-library typed value (for example, a frozen
dataclass) is the preferred representation; K0 established no model-library
convention, and adding Pydantic solely for this proposal is not required.

Tests provide an active Team, applicable TeamPolicy/source configuration, and
a running `ingest_source` Task with its documented Team association, policy
version, allowed writes, and budget fields. These fixture records are
preconditions, not K1 production lifecycle/runtime behavior.

### K1 validation and persistence

Before commit, deterministically validate that:

- the Task exists, is `running`, has type `ingest_source`, and belongs to the
  Team whose policy version is recorded on the Task;
- the Team is active, the Task's policy version belongs to that Team, and the
  source identity matches a source in that policy version;
- the Task's business write scope permits Signal creation, and the `ingest_source`
  row in the scope matrix permits its associated Snapshot (K) and Event (K).
  Snapshot and Event are not added to the worker's `allowed_writes`;
- the operation does not exceed the Task budget. K1 performs no model/tool
  calls and adds no cost ledger or budget-accounting runtime;
- the claimed hash matches SHA-256 of the fetched bytes, and the immutable
  Snapshot at the content-addressed reference either does not yet exist or
  contains the same bytes.

Re-read/revalidate commit preconditions in the database transaction. For a
deterministically invalid proposal, roll back any database work and persist a
reason-bearing `proposal_rejected` Event in a separate transaction; do not
create a Signal or a published Snapshot reference. Hash and source validation
must happen before writing the content object. If a commit-time rejection
occurs after the content object was written, an unreferenced immutable object
may remain under the same orphan rule. If rejection-Event persistence fails,
surface the database error. K1 does not implement Task creation, Task state
transitions, or deadline/queue enforcement.

The Signal's authoritative ingestion fields are `domain`, `source_type`,
`origin_url`, `fetched_at`, `content_hash`, and `snapshot_ref`. `domain` is
derived from the owning Team. `extracted_summary` is optional and
non-authoritative; K1 may leave it null or omit it. `embedding` and
`embedding_model` are projections and are not required or generated by K1.
The K1 fixture representation of `TeamPolicy.rules["sources"]` is a list of
objects with `origin_url` and `source_type`; this is a narrow implementation
choice for matching the proposal to its configured source, not a new
domain-pack or policy-schema contract.

### K1 Snapshot storage and atomicity

Use the architecture's development storage boundary (the object-storage row
in `docs/architecture.md` §10): immutable content in a local filesystem
store, addressed by a stable reference derived from SHA-256 of the exact
fetched bytes. Do not store Snapshot bytes in PostgreSQL. The filesystem root
is supplied to the storage helper by the caller; selecting a local directory
layout is an implementation detail, not a new architecture concept. Existing
content-addressed objects are verified and reused, never overwritten. Publish
a new object only after all bytes are written, using an atomic no-clobber
operation on the local filesystem. If the destination already exists, verify
it and reuse it; never expose a partially written object at the
content-addressed reference.

Persist the content-addressed object before committing database references.
The database transaction contains the Signal row and its success Event; the
Signal's `snapshot_ref` and `content_hash` identify the already-persisted
Snapshot object. On a database failure, roll back both database rows. A
process failure or rollback can leave an unreferenced immutable object in the
filesystem. This is permitted: committed database records define domain
visibility, and retries reuse the object. K1 does not add object garbage
collection. Thus the atomic unit is the committed database state, with the
precondition that a referenced Snapshot object is durable; it is not a
distributed transaction spanning PostgreSQL and the filesystem.

For identical `(origin_url, content_hash)`, the database uniqueness constraint
is the race-safe boundary. Reuse the existing Signal/Snapshot and emit the
documented `fetch_no_change` Event; concurrent losers resolve to that existing
Signal rather than creating a second one. Verify that its referenced object
exists and matches the stored hash; report missing/corrupt storage rather
than silently claiming success. If a concurrent insert loses the unique-key
race, roll back that transaction, re-read the winning Signal, then write the
no-change Event in a fresh transaction.

### K1 idempotency and Events

- Across Tasks, `(origin_url, content_hash)` identifies identical fetched
  content. The existing Signal is durable evidence of the prior ingestion.
- On retry, the Task's prior ingestion outcome Event is the idempotency marker.
  If the Task and proposal identity match a committed success or no-change
  outcome, return that outcome without another Signal or Event. A retry with a
  different proposal is not a replay of the committed operation; reject it
  with `proposal_rejected` reason `task_outcome_conflict` and preserve the
  recorded outcome.
- Serialize processing of the same Task by locking its existing Task row
  during the database transaction. After acquiring the lock, check for the
  prior outcome Event before inserting. The lock is a K1 transaction detail,
  not Task-runtime behavior.
- Every Event has a Task reference. Use `fetch_no_change` for identical
  content, as named in `docs/tasks.md` and `docs/walkthrough.md`. The
  walkthrough uses `proposal_rejected` for a rejected proposal; the
  architecture requires commit-rejection Events with reasons but does not fix
  a string type name. Use `proposal_rejected` for K1 rejection. The
  successful-ingestion Event name is not fixed by the architecture;
  `signal_ingested` is the K1 local event-type choice.
- Include Task ID and the source identity/content hash in the Event payload;
  success also identifies the Signal and Snapshot reference, while rejection
  includes a stable reason. Retrying a recorded outcome emits no additional
  Event.
- A rejection Event requires an existing Task to reference. If the proposal
  does not identify an existing Task, fail explicitly without writing domain
  state; an unattributable Event cannot satisfy the Event foreign key or
  provenance requirement.

### K1 schema and implementation organization

The ingestion commit requires only:

- a Signal table with the authoritative ingestion fields above and a unique
  `(origin_url, content_hash)` constraint;
- an Event table with Task foreign key, type, payload, and creation time;
- content-addressed Snapshot bytes in the local filesystem. No separate
  Snapshot table is required for K1: `Signal.snapshot_ref` and
  `Signal.content_hash` are the persisted reference/metadata.

Use one PostgreSQL migration after `0001_enable_pgvector`. For consistent
table naming, the K1 implementation choice is lower-case plural table names
and UUID primary keys. Create only these fields:

Create tables in dependency order: `teams`, `team_policies`, `tasks`,
`signals`, `events`; drop them in reverse order on downgrade. The
`team_policies` composite unique key must exist before adding the Task
composite foreign key.

| Table | Required columns and constraints | Purpose / authority |
|---|---|---|
| `teams` | `id UUID PRIMARY KEY`, `domain TEXT NOT NULL`, `status TEXT NOT NULL` | Fixture prerequisite. The Team row is authoritative; K1 validates `active` and derives Signal domain from it. No Team lifecycle code. |
| `team_policies` | `id UUID PRIMARY KEY`, `team_id UUID NOT NULL REFERENCES teams(id)`, `version INTEGER NOT NULL`, `rules JSONB NOT NULL`, `UNIQUE(team_id, version)` | Fixture prerequisite. The version referenced by the Task and its source list are authoritative configuration. `rules.sources` uses the narrow K1 fixture shape described above. No policy lifecycle. |
| `tasks` | `id UUID PRIMARY KEY`, `team_id UUID NOT NULL REFERENCES teams(id)`, `task_type TEXT NOT NULL`, `status TEXT NOT NULL`, `policy_version INTEGER NOT NULL`, `allowed_writes JSONB NOT NULL`, `budget JSONB NOT NULL`, `FOREIGN KEY(team_id, policy_version) REFERENCES team_policies(team_id, version)` | Fixture prerequisite and provenance. Stores only fields read by K1 checks; no Task creation, lifecycle service, attempt counter, or budget ledger. |
| `signals` | `id UUID PRIMARY KEY`, `domain TEXT NOT NULL`, `source_type TEXT NOT NULL`, `origin_url TEXT NOT NULL`, `fetched_at TIMESTAMPTZ NOT NULL`, `content_hash TEXT NOT NULL CHECK (content_hash ~ '^sha256:[0-9a-f]{64}$')`, `snapshot_ref TEXT NOT NULL`, `UNIQUE(origin_url, content_hash)` | Authoritative ingestion record. The unique pair resolves identical-content races. No summary or embedding columns are required for K1. |
| `events` | `id UUID PRIMARY KEY`, `task_id UUID NOT NULL REFERENCES tasks(id)`, `type TEXT NOT NULL`, `payload JSONB NOT NULL`, `created_at TIMESTAMPTZ NOT NULL`; index on `(task_id, type)` | Authoritative audit and Task-idempotency record. Do not add a separate idempotency table or uniqueness constraint that would prohibit multiple event types per Task. |

Snapshot bytes are files, not rows: the content hash and stable reference on
Signal are the K1 database metadata. For this implementation the stable
reference format is `snap://sha256/<64-lowercase-hex-digest>`; the filesystem
key is derived from that digest under the caller-supplied root. This format and
path mapping are local K1 implementation choices, not a general Snapshot URI
standard. Verify an existing object byte-for-byte (and by hash) before reuse.
Never overwrite it. A same-Task retry may write/check the content-addressed
object before it obtains the Task-row lock; this is safe because the object
write is immutable and idempotent.

Team, TeamPolicy, and Task tables exist only to construct referentially valid
fixture state and run K1 validation. These fields do not implement their
production lifecycle. Do not add other entity tables or fields to this
migration.

The `rules.sources` fixture values use objects with exactly `origin_url` and
`source_type`; Task `allowed_writes` is a JSON array containing `Signal`.
The Task scope matrix separately authorizes the bounded Snapshot and
Task-attributed Event side effects through `K`; K1 code, not the worker,
creates them. Fixture inserts of Team, TeamPolicy, and Task do not exercise or
bypass production Task/scope runtime. The
Task `budget` JSON object contains the documented keys
`max_tool_calls`, `max_cost_usd`, and `deadline_seconds`. For this operation,
the work consumes zero tool calls and zero model cost. There is no usage
counter or deadline enforcement in K1.

The `content_hash` is serialized as `sha256:<64 lowercase hexadecimal
characters>`; the Snapshot file key uses just the hexadecimal digest. A
successful or `fetch_no_change` Event payload contains `origin_url`,
`source_type`, `content_hash`, `signal_id`, and `snapshot_ref` (Task ID is also
the Event foreign key). A `proposal_rejected` payload contains the stable
`reason` code and, when available, `origin_url`, `source_type`, the claimed
hash, and the computed hash. These payload fields support audit and replay
checks without creating a separate idempotency record.

The following file map is a proposed implementation organization, not an
architecture rule; K0 did not establish application-module conventions:

| Path | K1 role |
|---|---|
| `core/models.py` | Minimal SQLAlchemy mappings matching the table/column contract above. No Snapshot blob model or full lifecycle services. |
| `core/snapshot_store.py` | Small local-filesystem content-addressed put/read helper using the specified K1 reference format. It verifies existing bytes and never overwrites them; it is not a pluggable storage framework. |
| `core/ingestion.py` | Transient proposal, deterministic validation, duplicate/retry resolution, rejection Event, and transactional Signal/success-Event commit. |
| `migrations/versions/0002_ingestion_kernel.py` | Minimal K1 tables, foreign keys, unique constraints, and lookup indexes after the pgvector extension migration. |
| `tests/conftest.py` | Disposable PostgreSQL setup and fixture builders for active Team, matching policy/source, running Task, and temporary Snapshot directory. |
| `tests/test_ingestion.py` | Focused database-backed K1 contract tests. |

Acceptance:

- one green end-to-end commit path
- new content commits Signal and success Event together, referencing a durable
  immutable Snapshot;
- invalid proposals commit a reason-bearing `proposal_rejected` Event without
  a Signal or a published Snapshot reference;
- identical content under another Task emits `fetch_no_change` and creates no
  second Signal;
- replay of a Task's recorded outcome adds no duplicate Signal or Event;
- transaction failure leaves no partial database commit;
- INV-02, INV-03, INV-13, and INV-14 are preserved.

The walkthrough is a permitted source of fixture examples, not a production
bootstrap specification. Fixture inserts establish prerequisites outside the
ingestion transaction; assertions must exercise the production K1 validation
and commit path.

## Slice R2 — Objective model

Implement one durable Objective entity with its explicit lifecycle; Tasks may reference it, but no second ephemeral Objective abstraction exists.

Add a new migration after the immutable K1 migration `0002_ingestion_kernel`;
do not alter K1 schema or behavior. Add the nullable `tasks.objective_id`
reference in this slice. Objective creation and status transitions are
Task-attributed operations using the compatibility contract in
`docs/04-data-model-changes.md` and `docs/tasks.md`; all mutations remain
Kernel-validated. Concrete Task and Event names remain implementation choices.

Implement:

- Objective model
- repository
- state machine (`draft → active/cancelled`; `active → paused/blocked/completed/cancelled`; `paused → active/cancelled`; `blocked → active/cancelled`; completed/cancelled terminal)
- validation
- Events
- migration
- invariant tests

Acceptance:

```text
Objective is one durable entity
all specified lifecycle transitions work
unspecified transitions fail
completed and cancelled are terminal
every transition emits Event
```

Tests cover lifecycle success/rejection, same-Task replay, scope and
same-Team ownership rejection, atomic Objective/Event persistence, and
conflicting concurrent transitions. These tests establish R2 behavior only;
they do not imply that the full invariant suite is implemented.

## Slice R5 — Plan materialization

Add the Plan schema and nullable `tasks.plan_id` in a migration after the R2
Objective migration; do not backfill ordinary reactive Tasks into Plans. A
Plan requires its parent Objective. Task Objective and Plan references remain
independently optional; when both are present, they must be Team-consistent
and the Task Objective must match the Plan's parent Objective. Before
implementation, settle the intentionally deferred Plan status transitions,
dependency representation, mutation scope, and materialization replay behavior
in accordance with `docs/04-data-model-changes.md`.

Implement:

```text
StrategyProposal
    ↓
Plan
    ↓
Task[]
```

Plan materialization simply creates ordinary Tasks. Those Tasks then use the existing Task execution path.

Acceptance:

- dependencies are explicit
- Plan budget is within applicable TeamPolicy ceiling
- aggregate allocated/remaining Task budgets stay within Plan envelope
- each Task budget governs individual execution
- stop conditions are explicit
- Plan can be inspected after restart
- Plan is execution intent; Tasks/Events/Outcomes remain authoritative
